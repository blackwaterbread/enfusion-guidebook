<Objectives>

- Enforce Script가 어떤 언어이고 Python이나 JavaScript와 무엇이 다른지 설명할 수 있다.
- 스크립트 파일(`.c`)이 스크립트 모듈 단위로 컴파일된다는 점을 이해하고, 모드의 스크립트를 어느 폴더에 두는지 안다.
- Workbench에서 스크립트 파일을 만들고 Script Editor에서 컴파일한 뒤 실행 결과를 확인할 수 있다.
- 공식 LSP를 켜서 VS Code 같은 외부 편집기를 연결하는 방법과 현재의 한계를 안다.
- `TAG_` 접두사와 `m_` 접두사 같은 기본 이름 규칙을 지킬 수 있다.

</Objectives>

이 책은 Arma Reforger 모드를 만들 때 쓰는 Enforce Script를 처음부터 배우는 책입니다. 독자가 Python이나 JavaScript로 프로그램을 짜 본 경험이 있다고 보고, 이미 아는 개념은 짧게 넘기고 Enforce Script만의 규칙에 시간을 씁니다.

1장에서는 문법을 본격적으로 배우기 전에 큰 그림을 잡습니다. 언어가 어디에서 왔는지, 스크립트가 어떻게 컴파일되는지, 어떤 도구로 코드를 쓰는지 살펴본 뒤 Workbench에서 첫 스크립트를 실행합니다. 변수와 타입은 2장, 제어 흐름은 3장, 함수는 4장에서 이어집니다.

## Enfusion 엔진과 Enforce Script

### 어디에서 온 언어인가

Enfusion은 Bohemia Interactive가 만든 게임 엔진이고, Enforce Script는 이 엔진의 스크립트 언어입니다. Arma Reforger는 Enfusion 엔진으로 만든 게임입니다. 같은 회사의 DayZ도 Enforce Script를 쓰기 때문에 검색하면 DayZ용 자료가 많이 나오는데, 기본 문법은 거의 같지만 게임 API가 달라서 Arma Reforger 모드에 그대로 쓸 수 없습니다.

공식 위키는 Enforce Script를 "문법이 C#에 가깝고, C++에서 영감을 받았으며, 엔진에 가까운 언어"로 소개합니다.

### 언어의 첫인상

Enforce Script는 다음과 같은 특징을 가진 언어입니다.

- **정적 타입(static typing)**: 변수를 만들 때 타입을 정하고, 그 변수의 타입은 끝까지 바뀌지 않습니다.
- **C#과 비슷한 문법**: 중괄호로 블록을 만들고, 문장 끝에 세미콜론을 붙입니다.
- **클래스 기반 객체지향**: 실행되는 코드는 모두 함수 안에 있고, 함수는 대부분 클래스의 메서드입니다.
- **참조 카운팅(Reference Counting)**: Java나 C#의 가비지 컬렉션 대신, 객체를 가리키는 강한 참조가 없어지면 바로 지웁니다. 7장에서 자세히 다룹니다.
- **`modded` 클래스**: 게임의 원래 클래스를 직접 고치지 않고 내 모드의 클래스로 갈아 끼웁니다. 12장에서 다룹니다.

짧은 클래스 하나로 첫인상을 확인해 보겠습니다. 아직 모든 줄을 이해하지 않아도 됩니다.

```enforce
//! 탄약 수를 관리하는 간단한 클래스
class TAG_AmmoCounter
{
	protected int m_iAmmo = 30;

	//------------------------------------------------------------------------------------------------
	bool Fire()
	{
		if (m_iAmmo <= 0)
			return false;

		m_iAmmo--;
		return true;
	}

	//------------------------------------------------------------------------------------------------
	int GetAmmo()
	{
		return m_iAmmo;
	}
}
```

`int`, `bool` 같은 타입이 변수와 반환값 앞에 붙고, 멤버 변수에는 `m_` 접두사가 붙습니다. 메서드 사이의 긴 주석 줄과 `//!` 문서 주석은 공식 코딩 컨벤션을 따른 것입니다.

### Python과 JavaScript 개발자가 낯설어하는 점

다음 표는 이 책을 읽으며 자주 부딪히게 될 차이를 미리 모은 것입니다. 자세한 내용은 오른쪽에 적힌 장에서 다룹니다.

| 낯선 점 | 내용 | 자세히 |
|---|---|---|
| 최상위 코드가 없음 | 실행할 코드는 모두 함수 안에 있어야 합니다. 파일 맨 위에 `Print(...)`를 쓰면 컴파일 오류가 납니다. | 2장 |
| `import`가 없음 | 같은 스크립트 모듈의 파일은 모두 함께 컴파일되므로 다른 파일의 클래스를 이름만으로 씁니다. | 1장 |
| 타입이 고정됨 | 변수의 타입은 바뀌지 않습니다. `int` 변수에 문자열을 넣으면 컴파일러가 경고만 내고 0이나 1을 넣습니다. | 2장 |
| 삼항 연산자가 없음 | `c ? a : b`는 컴파일 오류입니다. `if`/`else`로 씁니다. | 2장 |
| 멤버 변수의 기본 참조가 약함 | `ref` 없이 멤버 변수에 담은 객체는 사라질 수 있습니다. `new`로 만든 객체를 바로 넣으면 컴파일러가 막습니다. | 7장 |
| 예외 처리 구문이 없음 | `try`/`catch`가 없습니다. 잘못된 접근은 가상 머신 예외(VM Exception)로 나타납니다. | 15장 |
| 대소문자를 엄격히 구분 | `print("ok");`와 `Print("ok");`는 다릅니다. | 1장 |

<Compare title="같은 일을 하는 짧은 함수">

```python
def describe(name, health):
    return f"{name}: {health} HP"
```

```javascript
function describe(name, health) {
  return `${name}: ${health} HP`;
}
```

```enforce
class TAG_Describer
{
	static string Describe(string name, int health)
	{
		return name + ": " + health + " HP";
	}
}
```

</Compare>

Enforce Script 쪽은 매개변수와 반환값의 타입을 적고, 함수를 클래스 안에 둡니다. 문자열 안에 값을 끼워 넣는 문법이 없어서 `+`로 이어 붙이거나 `string.Format`을 씁니다(9장).

## 스크립트가 컴파일되고 실행되는 방식

### `.c` 파일과 스크립트 모듈

Workbench의 파일 형식 문서에 따르면 Enforce Script 파일의 확장자는 `.c`입니다. C 언어 파일과 확장자만 같을 뿐 관계는 없습니다.

스크립트는 **스크립트 모듈(script module)** 단위로 컴파일됩니다. 어떤 모듈이 어느 폴더를 읽는지는 Arma Reforger의 `.gproj` 설정에 정해져 있습니다. 공식 위키가 소개하는 모듈과 폴더는 다음과 같습니다.

| 모듈 | 폴더 | 공식 스크립트에 들어 있는 것 |
|---|---|---|
| `core` | `Core` | 기본 타입과 엔진 핵심 API(`Print`, `array`, `map`, 수학, 엔티티 기본 클래스 등) |
| `gameLib` | `GameLib` | `Game` 클래스, 입력·메뉴 관리, 리플리케이션 같은 게임 공통 기반 |
| `game` | `Game`, `GameCode` | Arma Reforger 게임 스크립트. `SCR_`로 시작하는 클래스 대부분 |
| `workbench` | `Workbench` | Workbench 플러그인과 도구 |
| `workbenchGame` | `WorkbenchGame` | 게임용 Workbench 플러그인과 도구 |

위키는 이 폴더 밖에 둔 스크립트는 그냥 무시된다고 경고합니다. 모드의 스크립트는 거의 항상 `Scripts/Game` 아래에 둡니다. 컴포넌트와 엔티티 스크립트는 `Game` 모듈에 있어야 Workbench의 목록에 나타난다는 점도 공식 위키가 강조합니다(10장).

### `import` 없이 함께 컴파일된다

Python이나 JavaScript에서는 다른 파일의 코드를 쓰려면 `import`가 필요합니다. Enforce Script에는 `import`나 `using` 같은 키워드가 없습니다. 같은 모듈에 속한 `.c` 파일은 모두 함께 컴파일되므로, 다른 파일에 정의한 클래스도 이름만 적으면 바로 쓸 수 있습니다.

파일 내용을 그대로 끼워 넣는 전처리기 지시문 `#include`는 있지만, 공식 스크립트는 이를 쓰지 않습니다(부록 A). 모든 클래스가 사실상 하나의 이름 공간을 나눠 쓰기 때문에 클래스 이름이 겹치면 안 됩니다. 이것이 뒤에서 설명할 `TAG_` 접두사가 필요한 이유입니다.

### 컴파일과 실행

스크립트는 컴파일된 뒤 엔진 안의 스크립트 가상 머신(VM)에서 실행됩니다. 문법 오류는 컴파일할 때 드러나고, `null` 객체에 접근하는 것 같은 실행 중 오류는 가상 머신 예외로 나타납니다. Script Editor의 **Build** 메뉴에는 오류만 검사하는 **Validate Scripts**와 다시 컴파일해 불러오는 **Validate and Reload Scripts**가 있습니다.

컴파일된 코드는 저절로 실행되지 않습니다. 엔진이 엔티티와 컴포넌트의 이벤트를 부르거나(10장), 게임 모드가 콜백을 부르거나(11장), 내 `modded` 클래스가 원래 클래스 대신 쓰일 때(12장) 실행됩니다. 이 장에서는 테스트용으로 Script Editor의 콘솔에서 직접 실행합니다.

## 애드온 프로젝트 최소한으로 이해하기

모드는 Workbench에서 **애드온(addon)** 프로젝트로 만듭니다. 이 절에서는 첫 스크립트를 둘 자리를 마련할 만큼만 살펴봅니다. 리소스와 의존성을 포함한 전체 작업 흐름은 12장에서 다룹니다.

### 프로젝트 만들기

Steam에서 **Arma Reforger Tools**를 실행하면 Workbench 런처가 열립니다. 런처의 **Add Project** ▾ 메뉴에서 **Create New Project**를 골라 이름을 정하고, 기본 의존성(dependency)인 Arma Reforger를 그대로 둔 채 **Create**를 누릅니다.

<Warning title="프로젝트 위치">

위키는 OneDrive 폴더에 만든 프로젝트를 불러오지 못한다고 경고하므로, 런처가 보여 주는 기본 위치가 OneDrive 안이 아닌지 확인하세요.

</Warning>

### `addon.gproj` 파일

새 프로젝트의 루트에는 프로젝트 설정 파일인 `addon.gproj`가 생깁니다. 공식 샘플 모드 `SampleMod_ModdedScript`의 `.gproj` 파일은 다음과 같습니다.

```text title="SampleMod_ModdedScript/SampleMod_ModdedScript.gproj"
GameProject {
 ID "SampleMod_ModdedScript"
 GUID "5614E482B37103E5"
 TITLE "Sample Mod - Modded Script"
 Dependencies {
  "58D0FB3206B6F859"
 }
 Configurations {
  GameProjectConfig PC {
  }
  GameProjectConfig HEADLESS {
  }
  GameProjectConfig XBOX_ONE {
  }
  GameProjectConfig XBOX_SERIES {
  }
  GameProjectConfig PS4 {
  }
 }
}
```

`ID`와 `TITLE`에는 프로젝트의 이름이 들어가고, `GUID`는 프로젝트를 구별하는 고유 값입니다. `Dependencies`에는 의존하는 프로젝트의 GUID가 들어갑니다. 공식 샘플 모드는 대부분 `58D0FB3206B6F859`를 의존성으로 두는데, 이것이 기본 의존성인 Arma Reforger 데이터의 GUID입니다. 의존성은 이 파일을 직접 고치기보다 Workbench에서 바꾸는 것이 위키가 안내하는 방법이며, 그 목록(**Dependencies**)은 Workbench 메인 창의 **File > Project Settings...** 화면에 있습니다.

### 스크립트를 둘 폴더

스크립트는 프로젝트 루트 아래 `Scripts/Game` 폴더에 둡니다. 이 책의 예제 프로젝트는 다음 구조를 기준으로 합니다.

```text
TAG_FirstMod/
├── addon.gproj
└── Scripts/
    └── Game/
        └── TAG_HelloWorld.c
```

공식 샘플도 같은 방식입니다. `SampleMod_ModdedScript`는 `Scripts/Game/GameMode/Scoring/Modded/` 아래에 파일을 둡니다. `Scripts/Game` 안에서는 하위 폴더를 자유롭게 만들어 관련 파일을 묶어도 됩니다.

## 개발 도구

### Workbench와 Script Editor

스크립트는 Workbench의 **Script Editor**에서 쓰고 컴파일합니다. 컴파일 오류는 **Errors** 창에, `Print`로 출력한 메시지는 **Output** 창에 나타나며, **Remote Console** 창에서는 코드를 직접 입력해 실행합니다. 모르는 클래스가 나오면 기호 위에서 <Kbd>Ctrl</Kbd>+클릭으로 공식 스크립트의 선언을 열어 읽어 보세요. Script Editor에는 디버거도 들어 있으며, 디버깅은 15장에서 다룹니다.

### 외부 편집기와 공식 LSP

VS Code 같은 익숙한 편집기로 Enforce Script를 쓰고 싶다면, Workbench Script Editor에 들어 있는 **LSP(Language Server Protocol)** 구현을 쓸 수 있습니다. LSP는 편집기와 "언어 서버"가 자동 완성, 오류 표시 같은 정보를 주고받는 공개 프로토콜입니다. Enfusion에서는 Script Editor가 LSP 서버 역할을 하고, 내 편집기는 TCP로 접속하는 클라이언트가 됩니다.

이 기능은 **실험 단계**입니다. 엔진 문서는 Script Editor가 여전히 주된 작성 도구이며, LSP의 모든 기능을 구현하는 것이 목표가 아니라 실험 중이라고 밝힙니다. VS Code 확장도 아직 WIP(작업 중) 상태이고, 정식 이름과 배포 경로는 나중에 정한다고 적혀 있습니다.

#### 연결 순서

엔진 문서가 안내하는 순서는 다음과 같습니다.

1. **Workbench Options에서 LSP를 켭니다.** 같은 화면에서 포트 번호도 확인합니다.
2. **Workbench를 띄워 둡니다.** LSP를 켜 두면 Script Editor 창을 따로 열지 않아도 Workbench가 접속을 받습니다. 문서는 나중에는 클라이언트가 서버를 자동으로 띄우게 바뀔 것이라고 예고합니다.
3. **편집기에서 TCP로 접속합니다.** 기본 포트는 5776입니다. 같은 PC에서 실행 중인 Workbench에 붙으므로 주소는 `127.0.0.1:5776`이 됩니다.
4. **프로젝트의 `.c` 파일을 엽니다.** 파일은 실제로 디스크에 있어야 하고, 프로젝트의 올바른 스크립트 폴더 안에 있어야 합니다.

Workbench를 명령줄에서 실행할 때 `-lsp`를 붙이면 시작과 함께 LSP 서버가 켜지고, `-lspPort 포트번호`로 포트를 바꿀 수 있습니다. 엔진 문서에 따르면 이 매개변수로 켠 서버는 Workbench 안에서 끄거나 포트를 바꿀 수 없습니다.

#### VS Code 설정

VS Code용 확장은 VSIX 파일로 설치합니다. 확장(Extensions) 보기에서 **Views and More Actions...** 메뉴의 **Install from VSIX...** 항목을 고르거나, 명령줄에서 다음처럼 설치합니다.

```powershell
code --install-extension <확장 파일 이름>.vsix
```

설치한 뒤 프로젝트의 `.c` 파일을 열고, 오른쪽 아래 상태 표시줄의 언어가 `Enforce`인지 확인합니다. 다르면 직접 `Enforce`로 바꿉니다. 클라이언트를 다시 시작하려면 <Kbd>Ctrl</Kbd>+<Kbd>Shift</Kbd>+<Kbd>P</Kbd>로 명령 팔레트를 열고 **LSP Client restart**를 실행하거나 기본 단축키 <Kbd>Ctrl</Kbd>+<Kbd>Alt</Kbd>+<Kbd>D</Kbd>를 누릅니다.

연결이 안 될 때 문서가 가장 먼저 꼽는 원인은 포트 번호입니다. 확장 목록에서 `lsp-enforcescript-extension`의 설정을 열어, 확장에 적힌 포트와 Workbench 옵션의 포트가 같은지 확인합니다. 엔진 문서에는 Neovim 설정 페이지도 따로 있으므로, 다른 편집기도 TCP 클라이언트로 같은 주소에 붙이면 됩니다.

#### 지원하는 기능

엔진 문서의 기능 목록을 정리하면 다음과 같습니다.

| 기능 | 설명 |
|---|---|
| 파일 열기와 닫기 | `.c` 파일을 다룹니다. |
| 파일 저장 | 저장은 클라이언트가 아니라 LSP 서버(Script Editor)가 합니다. |
| 변경 동기화 | 편집기에서 바꾼 내용이 Script Editor와 동기화됩니다. 주로 디버깅을 위한 기능입니다. |
| 진단(Diagnostic) | 프로젝트의 오류와 경고를 받습니다. 모든 `.c` 파일을 저장해야 완전한 진단이 오고, 저장하기 전에는 문법·어휘 오류만 옵니다. |
| 자동 완성 | 키워드와 기본 타입뿐 아니라 클래스, 열거형 등의 정보도 제안합니다. |
| 시그니처 도움말 | 메서드를 호출할 때 매개변수 이름과 오버로드 목록, 지금 입력 중인 매개변수를 보여 줍니다. |
| 호버(Hover) | 커서 아래 기호의 시그니처와 Doxygen 문서 주석을 보여 줍니다. |
| 정의로 이동 | Go to Definition, Go to Type Definition, Go to Implementation을 지원합니다. Implementation은 오버라이드가 여러 개면 목록을 돌려줍니다. |

<Warning title="실험 기능의 한계">

- Script Editor는 디스크에 저장된 코드만 컴파일할 수 있습니다. 그래서 외부 편집기로 편집 중인 파일에 서버가 직접 쓰기 작업을 하며, 문서는 이것이 편집기에서 예상하지 못한 결과를 낼 수 있다고 경고합니다.
- Workbench가 실행 중이어야 합니다.
- 디스크에 실제로 있는 파일에만 연결되고, 스크립트가 프로젝트의 올바른 폴더에 있어야 합니다.
- 일부 기능은 서버와 클라이언트가 같은 파일 시스템을 쓴다고 가정합니다.

</Warning>

## 첫 스크립트 실행하기

공식 위키의 Scripting First Steps는 월드를 불러오지 않고도 Script Editor의 Remote Console에서 간단한 코드를 바로 실행해 볼 수 있다고 안내합니다. 먼저 콘솔에서 한 줄을 실행하고, 이어서 스크립트 파일을 만들어 봅니다.

### 콘솔에서 한 줄 실행하기

Workbench의 **Editors** 메뉴에서 **Script Editor**를 열고, **Remote Console**에 `Print("Hello there!");`를 입력한 뒤 **Run**을 누르면 **Output** 창에 `Hello there!`가 나타납니다.

`Print`는 인수로 받은 값을 로그에 출력하는 전역 함수입니다. 콘솔은 입력한 코드를 그 자리에서 실행해 주는 특별한 환경입니다. 스크립트 파일에서는 이렇게 맨 바깥에 실행문을 쓰면 컴파일 오류가 나므로, 함수 안에 넣어야 합니다.

### 스크립트 파일 만들기

이번에는 프로젝트에 스크립트 파일을 만들고, 그 안의 메서드를 콘솔에서 부릅니다. 공식 위키의 Scripting Example이 안내하는 방식입니다.

Resource Browser의 **Create** 버튼에서 **Script**를 골라 `Scripts/Game` 폴더에 `TAG_HelloWorld.c`를 만들고 다음 내용을 씁니다.

```enforce title="Scripts/Game/TAG_HelloWorld.c"
//! 1장 첫 스크립트. Remote Console에서 TAG_HelloWorld.SayHello(); 로 호출합니다.
class TAG_HelloWorld
{
	//------------------------------------------------------------------------------------------------
	static void SayHello()
	{
		Print("Hello, Enforce Script!");
		PrintFormat("%1 + %2 = %3", 2, 3, 2 + 3);
	}
}
```

파일을 저장하고 **Build > Validate and Reload Scripts**로 컴파일합니다. Errors 창에 오류가 없으면 Remote Console에 다음 한 줄을 입력합니다.

```enforce
TAG_HelloWorld.SayHello();
```

콘솔의 실행 환경을 **Game**으로 두고 **Run**을 누릅니다. 1.8.0.13에서는 위키의 안내와 달리 **Run** 뒤에 따로 컴파일하지 않아도 Output에 다음 결과가 바로 나왔습니다.

```text
Hello, Enforce Script!
2 + 3 = 5
```

<Pitfall title="파일 맨 위에는 실행문을 쓸 수 없다">

Python 스크립트처럼 파일 맨 위에 실행문을 쓰면 컴파일 오류(`Syntax error`)가 납니다. 엔진 문서는 "모든 코드는 함수 안에 선언해야 한다"고 정해 두었습니다.

```enforce
Print("Hello");  // [!code --]

class TAG_HelloWorld
{
	static void SayHello()
	{
		Print("Hello");  // [!code ++]
	}
}
```

</Pitfall>

### Print와 PrintFormat

두 함수의 선언은 `Core/proto/EnDebug.c`에 있습니다.

```enforce
proto void Print(void var, LogLevel level = LogLevel.NORMAL);
proto void PrintFormat(string fmt, void param1 = NULL, void param2 = NULL, void param3 = NULL,
	void param4 = NULL, void param5 = NULL, void param6 = NULL, void param7 = NULL,
	void param8 = NULL, void param9 = NULL, LogLevel level = LogLevel.NORMAL);
```

`proto`는 엔진(C++) 쪽에 구현된 함수라는 표시입니다. 매개변수 타입 `void`는 어떤 타입의 값이든 받는다는 뜻으로 읽으면 됩니다. `PrintFormat`은 형식 문자열의 `%1`부터 `%9`까지를 뒤따르는 인수로 바꿔 출력합니다.

`Print`에 변수를 그대로 넘기면 값 앞에 타입과 변수 이름이 함께 찍힙니다. `string name = "Alpha";` 다음에 `Print(name);`을 실행하면 `string name = 'Alpha'`가 출력됩니다. 값만 출력하려면 `Print("Name: " + name);`처럼 문자열 식을 넘기거나 `PrintFormat`을 씁니다.

두 번째 인수 `level`은 로그 수준입니다. `LogLevel` 열거형에는 `SPAM`, `VERBOSE`, `DEBUG`, `NORMAL`, `WARNING`, `ERROR`, `FATAL`이 있고, 기본값은 `NORMAL`입니다. `PrintFormat`처럼 앞에 기본값 매개변수가 많을 때는 이름을 붙여 `level`만 지정합니다. 이름 있는 인수(named argument)는 4장에서 다룹니다.

```enforce
Print("Config file not found", LogLevel.WARNING);
PrintFormat("Loaded %1 items", 12, level: LogLevel.VERBOSE);
```

<Note title="퍼센트 기호 출력하기">

`PrintFormat`에서 `%`는 특수 문자라서 `%`를 출력하려면 `%%`로 두 번 씁니다. 위키의 예에 따르면 `PrintFormat("%1%%", 5);`는 `5%`를 출력하고, `Print("5%");`는 그대로 `5%`를 출력합니다.

</Note>

## 이름 규칙 맛보기

공식 컨벤션(Scripting: Conventions)은 모든 클래스와 전역 함수에 **태그**(tag)를 붙이라고 정합니다. 앞에서 본 것처럼 모든 클래스가 이름 공간 하나를 나눠 쓰므로, 다른 모드와 이름이 겹치지 않게 하려는 규칙입니다. Bohemia Interactive의 스크립트에는 `SCR_` 태그가 붙어 있습니다. 모드 개발자는 아직 아무도 쓰지 않는 자기만의 태그를 정해야 하며, `SCR_` 같은 공식 태그나 다른 개발자가 이미 쓰는 태그를 쓰면 안 됩니다.

이 책은 태그 자리에 `TAG_`를 씁니다. 예제를 내 모드에 옮길 때는 `TAG_`를 내 태그로 바꾸세요. 자주 쓰는 규칙만 먼저 보면 다음과 같습니다.

```enforce title="Scripts/Game/TAG_PlayerScore.c"
//! 파일 이름과 클래스 이름이 같습니다.
class TAG_PlayerScore
{
	protected int m_iKills;                   // 멤버 변수: m_ + 타입 접두사
	protected float m_fAccuracy;
	protected string m_sPlayerName;

	protected static int s_iInstanceCount;    // 정적 변수: s_ + 타입 접두사

	const int MAX_KILLS = 9999;               // 상수: 대문자와 밑줄

	//------------------------------------------------------------------------------------------------
	void AddKills(int amount)                 // 메서드: PascalCase, 매개변수: camelCase
	{
		int newTotal = m_iKills + amount;     // 지역 변수: camelCase
		if (newTotal > MAX_KILLS)
			newTotal = MAX_KILLS;

		m_iKills = newTotal;
	}
}
```

타입 접두사는 `bool`은 `b`, `int`는 `i`, `float`는 `f`, `string`은 `s`, `vector`는 `v`, 열거형은 `e`, 배열은 `a`, 맵은 `m`입니다. 클래스 인스턴스는 `m_Entity`처럼 타입 접두사 없이 씁니다. 공식 컨벤션은 멤버를 멤버 변수, 정적 변수, 상수 순서로 두라고 정하며 위 예제도 그 순서를 따랐습니다. 전체 규칙표는 부록 A에, 모딩과 관련된 규칙은 12장에 있습니다.

## 이 책의 예제를 읽는 법

- **파일 경로**: 파일 하나를 통째로 보이는 예제는 제목에 애드온 루트 기준 경로를 적었습니다(`Scripts/Game/TAG_HelloWorld.c`).
- **일부만 보이는 코드**: 제목이 없는 짧은 예제는 메서드 본문이나 클래스 본문의 일부입니다. 실제로 실행하려면 이 장에서 본 것처럼 클래스와 메서드 안에 넣어야 합니다. 생략한 부분은 `// ...`로 표시합니다.
- **실행 결과**: `text` 블록에는 `Print`가 출력한 메시지 내용만 적습니다.
- **공식 선언 인용**: `proto void Print(...)`처럼 공식 스크립트의 선언을 그대로 옮긴 곳이 있습니다. `proto`, `external`, `native`는 엔진 쪽 구현을 뜻하는 수식어이고, 부록 A의 키워드 표에 정리했습니다.

## 정리

<Summary>

- Enforce Script는 Enfusion 엔진의 스크립트 언어로, 문법은 C#에 가깝고 정적 타입과 클래스 기반 객체지향을 씁니다.
- 스크립트 파일의 확장자는 `.c`이고, 스크립트 모듈(`core`, `gameLib`, `game`, `workbench`, `workbenchGame`) 단위로 함께 컴파일됩니다. `import`는 없습니다.
- 모드의 스크립트는 애드온 프로젝트의 `Scripts/Game` 아래에 둡니다. 모듈 폴더 밖의 스크립트는 무시됩니다.
- 실행할 코드는 모두 함수 안에 있어야 합니다. 테스트할 때는 Script Editor의 Remote Console에서 직접 실행할 수 있습니다.
- `Print(void var, LogLevel level = LogLevel.NORMAL)`와 `PrintFormat(fmt, ...)`로 Output 창에 로그를 남깁니다.
- Script Editor는 LSP 서버 역할도 하며, VS Code 같은 외부 편집기를 TCP(기본 포트 5776)로 연결할 수 있습니다. 아직 실험 기능이고 Workbench가 실행 중이어야 합니다.
- 클래스와 전역 함수에는 태그를 붙이고, 멤버 변수는 `m_`과 타입 접두사로 시작합니다.

</Summary>
