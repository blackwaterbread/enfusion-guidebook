<Objectives>

- `Print`, `PrintFormat`, `LogLevel`로 로그를 남기고 로그 파일의 위치와 출력 수준을 조절할 수 있다.
- Script Editor 디버거로 브레이크포인트를 걸고 단계 실행, 호출 스택, 변수 보기를 사용할 수 있다.
- Diag Menu에 직접 항목을 추가하고 디버그 도형과 텍스트로 상태를 그릴 수 있다.
- 스크립트 프로파일러와 시간 측정으로 느린 코드를 찾고, 공식 성능 지침에 따라 고칠 수 있다.
- Autotest Framework로 자동 테스트를 작성하고 실행할 수 있다.
- 컴파일 오류와 실행 중 오류(VME)의 흔한 원인을 찾을 수 있다.

</Objectives>

엔진 위에서 도는 스크립트는 언제 어떤 순서로 불리는지 눈에 보이지 않고, 14장에서 본 것처럼 같은 코드가 서버와 클라이언트에서 다르게 실행되기도 합니다. 이 장에서는 "지금 무슨 일이 일어나고 있는가"를 확인하는 도구를 차례로 익힙니다. 로그, 디버거, 게임 안의 시각화, 프로파일러, 자동 테스트 순서입니다.

## 로그 남기기

### Print와 PrintFormat

가장 기본 도구는 로그입니다. 두 함수의 선언은 `Core/proto/EnDebug.c`에 있습니다.

```enforce
proto void Print(void var, LogLevel level = LogLevel.NORMAL);

// param2부터 param8까지는 같은 꼴이라 줄였다
proto void PrintFormat(string fmt, void param1 = NULL, /* ... */ void param9 = NULL,
	LogLevel level = LogLevel.NORMAL);
```

`Print`는 값 하나를 출력하고, `PrintFormat`은 `%1`부터 `%9`까지의 자리표시자에 인수를 채워 출력합니다. 문자열 형식화의 자세한 규칙은 9장에서 다뤘습니다. 두 함수 모두 마지막에 심각도를 나타내는 `LogLevel`을 받습니다.

| `LogLevel` | 쓰임 |
|---|---|
| `SPAM`, `VERBOSE`, `DEBUG` | 평소에는 숨겨 둘 상세 정보 |
| `NORMAL` | 일반 메시지(기본값) |
| `WARNING` | 동작은 하지만 확인이 필요한 상황 |
| `ERROR` | 기능이 제대로 동작하지 못하는 상황 |
| `FATAL` | 계속 진행할 수 없는 상황 |

공식 주석(`ScriptInvokerBase.Dump()`)에 따르면 `DEBUG` 수준 로그를 보려면 로그 수준을 적어도 `DEBUG`로 설정해야 합니다(명령줄 `-logLevel debug`). 매개변수는 다음 절에서 정리합니다.

`PrintFormat`의 `level`은 형식 인수 9개 뒤에 있습니다. 그래서 공식 코드처럼 **이름 있는 인수**로 넘겨야 합니다.

```enforce
Print("발전기 컴포넌트를 찾지 못했습니다.", LogLevel.WARNING);
PrintFormat("플레이어 %1이 상자 %2를 열었습니다.", playerId, crateName, level: LogLevel.DEBUG);
```

<Pitfall title="PrintFormat에 LogLevel을 위치 인수로 넘긴다">

`PrintFormat("값: %1", value, LogLevel.WARNING)`이라고 쓰면 `LogLevel.WARNING`은 두 번째 형식 인수(`param2`) 자리에 들어갑니다. 메시지는 `NORMAL`로 기록되고, 경고 수준으로 걸러 보거나 검색할 때 빠지게 됩니다. `level: LogLevel.WARNING`처럼 이름을 붙여 넘기세요.

</Pitfall>

로그를 많이 남길 때는 어느 클래스에서 나온 메시지인지 알 수 있게 앞에 클래스 이름을 붙이면 찾기 쉽습니다. 공식 코드에도 `"[SCR_EmptyPositionHelper] ..."`처럼 쓴 예가 있습니다.

`Debug` 클래스에는 로그와 함께 쓰기 좋은 도우미가 있습니다.

| 메서드 | 하는 일 |
|---|---|
| `Debug.DumpStack()` | 현재 호출 스택을 로그에 출력합니다. `string`을 넘기면 그 변수에 담습니다. |
| `Debug.GetEntityLinkString(entity)` | 로그에 넣으면 클릭할 수 있는 링크가 되는 문자열을 만듭니다. 클릭하면 카메라가 그 엔티티로 이동합니다. |
| `Debug.Error(err)` | 오류 메시지 대화상자를 띄웁니다. |

1.8.0.13 Workbench에서 Script Editor를 연 세션의 플레이 모드에서 `Debug.Error()`를 불러 보면 VME(뒤에서 설명)로 보고되어 로그의 `Reason:` 줄에 메시지가 남았고, 실행은 다음 줄로 이어졌습니다.

### 로그는 어디에 남나

Workbench에서 실행하면 **Script Editor**의 **Output** 창에서 `Print` 결과를 볼 수 있습니다. 게임과 서버의 로그는 파일로도 남습니다. 공식 시작 매개변수 문서에 따르면 로그는 프로필 디렉터리 아래 `logs` 폴더에 저장되며, 관련 매개변수는 다음과 같습니다.

| 매개변수 | 설명 |
|---|---|
| `-profile` | 프로필 디렉터리 위치 |
| `-logsDir` | 로그 폴더 이름(프로필의 `logs` 아래) 또는 경로 |
| `-logLevel` | 출력할 최소 수준. `spam`, `verbose`, `debug`, `normal`, `warning`, `error`, `fatal` |
| `-logTime` | 줄마다 붙는 시간 형식. `none`, `time`(기본), `datetime` |
| `-keepNumOfLogs` | 남겨 둘 로그 개수(기본 10) |
| `-logAppend` | 시작할 때 로그를 지우지 않고 이어서 씀 |

## Script Editor 디버거

로그만으로 원인이 보이지 않으면 디버거로 실행을 멈추고 들여다봅니다.

### 브레이크포인트와 단계 실행

텍스트 편집기에서 줄 번호 옆을 클릭하거나 <Kbd>F9</Kbd>를 누르면 브레이크포인트가 걸립니다. 걸어 둔 브레이크포인트는 **Breakpoints** 창에 모이고, 체크박스로 켜고 끌 수 있습니다. 실행 중인 게임의 코드와 편집기의 코드가 맞지 않으면 브레이크포인트가 무효로 표시되고 멈추지 않습니다.

실행이 브레이크포인트에 닿으면 그 줄에 화살표가 나타나고, **Debug** 창의 버튼으로 실행을 이어 갑니다.

| 버튼 | 동작 |
|---|---|
| **Continue** | 다음 브레이크포인트까지 계속 실행 |
| **Step Over** | 함수 안으로 들어가지 않고 다음 줄로 |
| **Step Into** | 한 문장씩, 호출되는 함수 안으로 들어감 |
| **Step Out** | 지금 함수가 반환될 때까지 실행 |
| **Stop** | 플레이 모드와 디버깅 세션을 멈춤 |

멈춘 상태에서 변수에 마우스를 올리면 현재 값이 보이고, **Watch** 창에서 값을 계속 지켜볼 수 있습니다. **Callstack** 창은 지금 위치까지 어떤 메서드들을 거쳐 왔는지 보여 줍니다. 위키의 설명대로 **아래에서 위로** 읽으면 호출 순서가 됩니다.

<TryIt title="브레이크포인트로 발전기 따라가기">

14장의 `TAG_GeneratorComponent`를 붙인 엔티티가 있는 월드에서 해 봅니다.

1. **Script Editor**의 **Projects** 창에서 `TAG_GeneratorComponent.c`를 엽니다.
2. `OnPostInit()` 안의 `m_RplComponent = ...` 줄을 클릭하고 <Kbd>F9</Kbd>를 눌러 브레이크포인트를 겁니다. **Breakpoints** 창에 항목이 생겼는지 확인합니다.
3. World Editor에서 게임을 실행합니다. 엔티티가 초기화되면서 그 줄에서 실행이 멈춥니다. `OnPostInit()`은 편집 중에도 불리므로(10장) 월드를 편집하다가 멈출 수도 있는데, 그때는 **Continue**를 누릅니다.
4. `owner`에 마우스를 올려 어떤 엔티티인지 확인합니다.
5. **Watch** 창에서 `this`를 펼쳐 `m_RplComponent`를 봅니다. 멈춘 줄은 아직 실행되기 전이므로 값은 `NULL`입니다. 이 줄은 `OnPostInit()`의 마지막 문장이라, 여기서 **Step Over**를 누르면 다시 멈추지 않고 게임이 계속됩니다.
6. **Callstack** 창을 아래에서 위로 읽어 어떤 경로로 `OnPostInit()`이 불렸는지 확인하고, **Continue**로 실행을 재개합니다.

</TryIt>

### debug 키워드와 Remote Console

코드 안에 `debug;` 문을 쓰면 그 자리에서 Script Editor의 브레이크포인트가 걸립니다. 공식 AI 코드는 이 문장을 `#ifdef AI_DEBUG` 블록과 조건문 안에 두어 필요할 때만 멈추게 합니다.

```enforce
#ifdef TAG_DEBUG
	if (m_iRemaining < 0)
	{
		Print("남은 수량이 음수입니다.", LogLevel.ERROR);
		debug;	// 디버거가 연결되어 있으면 여기서 멈춘다
	}
#endif
```

`TAG_DEBUG` 같은 정의는 `-scrDefine TAG_DEBUG` 시작 매개변수로 켤 수 있습니다. 위키에 따르면 이 매개변수는 Workbench뿐 아니라 게임과 서버 실행 파일에서도 동작합니다.

**Remote Console** 창에서는 플레이 모드 중에 스크립트 코드를 바로 실행할 수 있습니다. 브레이크포인트에 멈춘 상태라면 그 인스턴스의 지역 문맥에서 실행되므로, 지역 변수를 써서 값을 계산해 볼 수 있습니다. 결과는 **Output** 창에 나옵니다.

### 게임과 서버에 디버거 연결하기

게임이 실행 중일 때 Script Editor를 열면 기본 포트로 디버거가 자동으로 연결됩니다. 다른 포트에 연결하려면 **Debug** 메뉴의 **Debug Custom**에서 포트를 입력합니다. 실행 파일 쪽 주소와 포트는 `-debugger`(기본 `localhost`)와 `-debuggerPort`(기본 1000) 매개변수로 정합니다.

Workbench 안의 게임이나 Peer Tool뿐 아니라 실제 클라이언트·서버도 디버깅할 수 있는데, 이때는 이름이 `Diag`로 끝나는 개발용 실행 파일(`ArmaReforgerSteamDiag.exe`, `ArmaReforgerServerDiag.exe`)을 써야 합니다. 위키에 따르면 Diag가 아닌 실행 파일은 Workbench 디버깅 도구에 연결할 수 없고, Diag 실행 파일과 섞어 접속할 수도 없습니다.

## 게임 안에서 보기: Diag Menu와 디버그 그리기

### Diag Menu

Diag Menu는 게임 스크립트와 애셋을 디버깅하기 위한 옵션을 모아 둔 메뉴입니다. Workbench의 3D 뷰포트(월드나 모델 미리보기)와 Diag 실행 파일에서 쓸 수 있습니다. 메뉴를 여는 단축키와 조작법은 위키 Diag Menu 문서의 General Use 항목에 있습니다. 스크립트 작업에 특히 쓸모 있는 항목은 다음과 같습니다.

| 경로 | 내용 |
|---|---|
| `Statistics > Script profiler` | 스크립트 프로파일러(`off`, `frame`, `average`, `memory`) |
| `Statistics > Slow script` | 느린 스크립트를 로그에 남길 기준 시간(`off`, `1ms` ~ `10ms`) |
| `Statistics > Verbose script Print` | 상세 스크립트 출력 켜기 |
| `GameCode > User Actions > Log actions` | 사용자 액션 로그 |
| `GameCode > User Actions > Context position` | 액션 컨텍스트 위치 표시 |
| `GameCode > Network > Log ownership changes` | 네트워크 소유권 변경 로그 |

자기 모드의 디버그 옵션도 Diag Menu에 넣을 수 있습니다. API는 `Core/generated/Debug/DiagMenu.c`의 `DiagMenu` 클래스입니다. 항목마다 정수 ID가 필요한데, 공식 게임 코드의 ID 열거형 `SCR_DebugMenuID`가 0부터 번호를 매기므로 따로 0부터 시작하는 열거형을 만들면 같은 번호를 쓰게 됩니다. 공식 Autotest 코드(`SCR_AutotestDebugMenu.c`)는 `modded enum SCR_DebugMenuID`로 항목을 덧붙이는 방식을 씁니다. 이 책도 그 방식을 따릅니다.

### 디버그 도형과 텍스트

월드 안에 선, 구, 화살표를 그리려면 `Shape` 클래스의 정적 메서드를 씁니다. 색은 `0xAARRGGBB` 형식의 정수이며 `Color.RED` 같은 상수를 쓸 수 있습니다.

| 메서드 | 그리는 것 |
|---|---|
| `Shape.CreateLine(color, flags, p1, p2)` | 선분 |
| `Shape.CreateSphere(color, flags, origin, radius)` | 구 |
| `Shape.CreateArrow(from, to, size, color, flags)` | 화살표 |
| `Shape.CreateCylinder(color, flags, origin, radius, length)` | Z축 방향 원기둥 |

`ShapeFlags`는 `|`로 조합합니다. `ShapeFlags.ONCE`를 주면 한 번 그려진 뒤 자동으로 사라지므로, `EOnFrame`처럼 매 프레임 불리는 곳에서 다시 그립니다. 공식 주석은 `ONCE`로 만든 도형의 참조를 보관하지 말라고 경고합니다. 반대로 `ONCE` 없이 계속 보여 줄 도형은, 공식 `SCR_MeleeComponent`처럼 반환된 `Shape`를 `array<ref Shape>` 같은 강한 참조에 보관해 두었다가 지울 때 배열을 비웁니다. `NOZBUFFER`는 다른 물체에 가려도 보이게, `WIREFRAME`은 선으로만 그리게 합니다.

글자는 `DebugTextWorldSpace.Create()`로 월드 좌표에, `DebugTextScreenSpace.Create()`로 화면 좌표에 씁니다. `DebugTextFlags.ONCE`를 주면 한 번만 그려지고 `null`이 반환됩니다. `ONCE` 없이 만든 텍스트는 공식 주석대로 `ref` 변수에 보관해야 나중에 지울 수 있습니다.

다음 컴포넌트는 Diag Menu의 `GameCode` 아래에 항목을 하나 추가하고, 그 항목이 켜져 있으면 발전기 위에 상태를 그립니다. 14장의 `TAG_GeneratorComponent`와 같은 엔티티에 붙여 씁니다.

```enforce title="Scripts/Game/TAG_GeneratorDebugComponent.c"
#ifdef ENABLE_DIAG
modded enum SCR_DebugMenuID
{
	TAG_DEBUGUI_GENERATOR_STATE
}
#endif

[ComponentEditorProps(category: "TAG/Tutorial", description: "발전기 상태 디버그 표시")]
class TAG_GeneratorDebugComponentClass : ScriptComponentClass
{
}

class TAG_GeneratorDebugComponent : ScriptComponent
{
#ifdef ENABLE_DIAG
	protected static bool s_bDiagRegistered;
	protected TAG_GeneratorComponent m_Generator;

	override void OnPostInit(IEntity owner)
	{
		if (!s_bDiagRegistered)
		{
			DiagMenu.RegisterBool(SCR_DebugMenuID.TAG_DEBUGUI_GENERATOR_STATE, "", "Generator state",
				"GameCode");
			s_bDiagRegistered = true;
		}

		m_Generator = TAG_GeneratorComponent.Cast(owner.FindComponent(TAG_GeneratorComponent));
		SetEventMask(owner, EntityEvent.FRAME);
	}

	override void EOnFrame(IEntity owner, float timeSlice)
	{
		if (!m_Generator || !DiagMenu.GetBool(SCR_DebugMenuID.TAG_DEBUGUI_GENERATOR_STATE))
			return;

		vector pos = owner.GetOrigin() + "0 2 0";
		int color = Color.RED;
		string text = "OFF";
		if (m_Generator.IsRunning())
		{
			color = Color.GREEN;
			text = "ON";
		}

		Shape.CreateSphere(color, ShapeFlags.ONCE | ShapeFlags.NOZBUFFER, pos, 0.3);

		DebugTextFlags flags = DebugTextFlags.ONCE | DebugTextFlags.CENTER | DebugTextFlags.FACE_CAMERA;
		DebugTextWorldSpace.Create(owner.GetWorld(), text, flags, pos[0], pos[1] + 0.6, pos[2],
			color: Color.WHITE);
	}
#endif
}
```

공식 코드는 진단용 코드를 이처럼 `#ifdef ENABLE_DIAG` 블록 안에 둡니다. 디버그 그리기는 화면이 있는 기계에서만 의미가 있고, 이 컴포넌트는 상태를 바꾸지 않으므로 서버와 클라이언트 어디서 실행해도 안전합니다. 클라이언트에서 보이는 `IsRunning()` 값은 14장에서 본 리플리케이션으로 받은 값입니다.

<Tip title="창 하나로 값 보기: DbgUI">

`DbgUI` 클래스(`Core/generated/Debug/DbgUI.c`)는 매 프레임 `DbgUI.Begin("제목")`과 `DbgUI.End()` 사이에 `DbgUI.Text()`, `DbgUI.Check()`, `DbgUI.Button()` 같은 호출을 넣어 작은 디버그 창을 만드는 즉시 모드(immediate mode) UI입니다. 값 몇 개를 계속 지켜볼 때 로그보다 편합니다. 1.8.0.13 Workbench의 Play에서 시험해 보면 창의 체크 상자와 버튼을 마우스로 누르려면 다른 메뉴(시험에서는 분대 창)를 열어 마우스 커서를 띄워야 했습니다.

## 프로파일링과 성능

### 느린 곳 찾기

- **스크립트 프로파일러**: Diag Menu의 `Statistics > Script profiler`로 켭니다. 외부 프로파일러 지원을 켜는 `-scriptExtProfiler` 시작 매개변수와 `Statistics > Script prof. external` 항목도 있지만, 위키의 Script Profiling 문서는 외부 프로파일러 안내를 삭제했습니다.
- **느린 스크립트 로그**: `Statistics > Slow script`에 기준 시간을 정하면 그보다 오래 걸린 스크립트가 로그에 남습니다.
- **메모리 할당 덤프**: `-checkInstance` 매개변수로 실행한 뒤 스크립트에서 `Debug.DumpInstances(true)`를 부르면, 할당된 스크립트 객체와 할당 위치가 CSV 형식으로 로그에 출력됩니다. 공식 주석대로 `-checkInstance` 없이는 동작하지 않습니다.

의심 가는 구간이 있으면 직접 재 볼 수도 있습니다. `System.GetTickCount()`는 게임이 시작된 뒤 지난 시간을 밀리초로 반환합니다.

```enforce
int start = System.GetTickCount();
RebuildCache();		// 재고 싶은 작업

// DEBUG 수준이므로 -logLevel debug로 실행해야 보인다
PrintFormat("RebuildCache: %1 ms", System.GetTickCount() - start, level: LogLevel.DEBUG);
```

`Debug.BeginTimeMeasure()`와 `Debug.EndTimeMeasure(제목)`으로 구간을 재는 방법도 있습니다. 공식 `SCR_TimeMeasurementHelper` 클래스의 주석에 사용 예가 있습니다.

### 성능 지침

위키의 Scripting: Performance 문서는 성능 문제를 다섯 가지 질문으로 점검하라고 권합니다.

| 질문 | 아니라면 |
|---|---|
| 꼭 필요한가? | 하지 않거나 더 단순한 코드로 바꾼다 |
| 여기서 해야 하나? | 그 일을 맡을 클래스로 옮긴다(단일 책임 원칙) |
| 이만큼 해야 하나? | 구조를 바꿔 연산 횟수를 줄인다 |
| 지금 당장 해야 하나? | 여러 프레임에 나눠 처리하고 결과를 저장해 둔다 |
| 이렇게 자주 해야 하나? | 몇 초마다 한 번 실행하고, 그 사이에는 저장한 결과를 쓴다 |

같은 문서는 큰 배열을 한꺼번에 도는 반복, 매 프레임 실행되는 코드, 10km 레이캐스트 같은 비싼 요청을 대표적인 문제로 꼽습니다. 공식 코드와 엔진 문서에서 확인할 수 있는 습관 몇 가지를 덧붙입니다.

- **`FindComponent()` 결과는 저장해 둡니다.** 공식 샘플의 사용자 액션은 모두 `Init()`에서 컴포넌트를 찾아 멤버 변수에 담아 둡니다.
- **매 프레임 할 필요가 없으면 `EOnFrame`을 쓰지 않습니다.** 엔진 문서는 이런 엔티티가 많으면 `EOnFrame` 호출이 상당한 시간을 차지할 수 있다고 지적하고, 몇 초 단위의 주기라면 `ScriptCallQueue.CallLater()`를 쓰라고 권합니다. 콜 큐는 11장에서 다뤘습니다.
- **조건에 맞지 않으면 일찍 빠져나옵니다.** 반복문에서도 필요 없는 항목은 `continue`로 건너뜁니다.
- **네트워크 대역폭은 가장 부족한 자원입니다.** 엔진 문서의 표현입니다. 복제할 데이터는 프레젠테이션에 꼭 필요한 최소한으로 줄입니다(14장).

다음은 매 프레임 주변을 검사하던 코드를 0.5초마다 검사하도록 바꾼 예입니다.

```enforce
override void OnPostInit(IEntity owner)
{
	SetEventMask(owner, EntityEvent.FRAME);										// [!code --]
	GetGame().GetCallqueue().CallLater(CheckNearby, 500, true);	// [!code ++]
}

override void EOnFrame(IEntity owner, float timeSlice)	// [!code --]
{														// [!code --]
	CheckNearby();										// [!code --]
}														// [!code --]

override void OnDelete(IEntity owner)
{
	GetGame().GetCallqueue().Remove(CheckNearby);	// 반복 호출을 반드시 해제
}
```

`CallLater`의 세 번째 인수 `true`가 반복 실행을 뜻합니다. 반복 호출은 컴포넌트가 삭제될 때 `Remove()`로 해제해야 합니다. 또 `OnPostInit()`은 World Editor 편집 중에도 불리므로(10장), 게임 중에만 돌아야 하는 타이머라면 등록하기 전에 `GetGame().InPlayMode()`로 걸러 냅니다.

## 자동 테스트

### Script Testing Framework

엔진에는 Script Testing Framework가 들어 있습니다(`GameLib/tests/TestingFramework.c`). 구성 요소는 다음과 같습니다.

- **테스트(test)**: `TestBase`를 상속하고 `[Test(suite: 스위트클래스)]` 어트리뷰트를 붙인 클래스입니다. 여러 틱에 걸쳐 실행될 수 있고, 상태는 멤버 변수에 둡니다.
- **스텝 메서드(step method)**: 테스트의 실제 로직입니다. 이름은 자유롭게 짓고 `[TestStep(TestStage.Main)]`처럼 단계를 지정합니다. `void`를 반환하면 한 번만, `bool`을 반환하면 `true`를 반환할 때까지 매 틱 실행됩니다.
- **단계(stage)**: `TestStage.Setup` → `Main` → `TearDown` 순서로 실행되고, 단계 안에서는 정의한 순서대로 실행됩니다. `Main`에서 실패하면 남은 `Main` 스텝을 건너뛰고 `TearDown`이 불립니다. `TestingFramework.c`의 공식 주석은 `Setup`이 실패하면 `TearDown`이 불리지 않는다고 적지만, 1.8.0.13에서 실행해 보면 `Setup` 스텝에서 `SetFailure()`로 실패를 설정해도 남은 `Setup`·`Main` 스텝만 건너뛰고 `TearDown`은 불렸습니다.
- **실패**: `SetFailure(TestFailureBase)`로 알립니다. 실패를 설정하면 그 단계가 끝납니다. 엔진 문서에 나오는 `SetResult()`는 1.8 스크립트에서 더 이상 쓰지 않는(`Obsolete`) 메서드입니다.
- **시간 제한**: 기본적으로 없으며, `Test`나 `TestStep` 어트리뷰트의 `timeoutS`, `timeoutMs`로 정합니다.

### Autotest Framework로 테스트 쓰기

Arma Reforger는 이 프레임워크를 확장한 Autotest Framework를 제공합니다. 테스트 스위트는 `SCR_AutotestSuiteBase`, 테스트 케이스는 `SCR_AutotestCaseBase`를 상속합니다. 케이스 클래스에는 조건이 거짓이면 실패를 기록하는 `AssertTrue(bool expression, string msg)`와, 메시지로 실패를 기록하는 `SetFailure(string reason, ...)`가 있습니다. 위키는 스위트 이름을 `SCR_TEST_기능Suite`, 케이스 이름을 `SCR_TEST_기능_상황_기대결과` 형태로 지으라고 권합니다. 직접 만드는 클래스에는 `SCR_` 대신 자기 태그를 씁니다.

다음은 단순한 계산 클래스를 검사하는 테스트입니다. 공식 예제(`Game/Tests/TestSuites/Example/SCR_TEST_Example1TestSuite.c`)처럼 `#ifdef WORKBENCH`로 감싸 Workbench에서만 컴파일되게 합니다.

```enforce title="Scripts/Game/Tests/TAG_TEST_SupplyMathSuite.c"
#ifdef WORKBENCH

class TAG_TEST_SupplyMathSuite : SCR_AutotestSuiteBase
{
}

[Test(suite: TAG_TEST_SupplyMathSuite)]
class TAG_TEST_SupplyMath_TakeAll_RemainingIsZero : SCR_AutotestCaseBase
{
	[TestStep(TestStage.Main)]
	void Execute()
	{
		int capacity = 3;
		int taken = 3;
		AssertTrue(TAG_SupplyMath.GetRemaining(capacity, taken) == 0, "다 가져가면 0이어야 한다");
		AssertTrue(TAG_SupplyMath.GetRemaining(capacity, 5) == 0, "음수가 되면 안 된다");
	}
}

#endif
```

`TAG_SupplyMath`는 테스트할 대상 클래스로, 16장 프로젝트에서 쓰는 계산을 떼어 낸 것이라고 생각하면 됩니다. 연습문제 15-5에서 직접 만들어 봅니다.

위키의 Autotest 문서에는 `[Step(EStage.Setup)]`, `SCR_AutotestResult.AsFailure()` 같은 이름이 나오지만, 1.8 공식 스크립트에는 이런 이름이 없습니다. 이 책처럼 `TestStep`, `TestStage`, `AssertTrue`, `SetFailure`를 쓰세요.

### 테스트 실행하기

공식 스크립트에는 테스트를 실행하는 도구가 세 가지 들어 있습니다(`Autotest/WorkbenchGame/TestFramework`, `Autotest/Game/TestFramework`).

- **Autotest 플러그인**: Script Editor와 World Editor의 플러그인으로, 커서가 놓인 테스트 스위트나 테스트 케이스를 실행합니다. `SCR_Autotest`로 시작하는 기반 클래스를 쓴 테스트만 지원하며, 플러그인 선언에는 단축키 <Kbd>F4</Kbd>가 지정되어 있습니다. 기본 설정에서는 실행이 끝나면 결과 대화상자가 열립니다.
- **Autotest Tool**: World Editor 도구로, 테스트 그룹 설정 파일을 고르거나 클래스 이름을 입력한 뒤 **Run group** 또는 **Run class**를 누릅니다.
- **`-autotest` 매개변수**: 명령줄에서 테스트 그룹, 스위트 클래스 이름, 케이스 클래스 이름 가운데 하나를 넘겨 실행합니다.

Autotest 플러그인과 Autotest Tool은 Workbench 안에서 실행할 때 플레이 모드로 바꿉니다. 1.8.0.13 Workbench에서 실행해 보면 케이스는 플레이 모드가 시작된 뒤에야 돌았고, `GetWorldFile()`을 오버라이드하지 않은 스위트는 그 전에 기본 Autotest 월드를 열었습니다.

## 오류 읽기

### 컴파일 오류

**Build** 메뉴의 **Validate Scripts**나 **Validate and Reload Scripts**를 실행하면 문제가 **Errors** 창에 모입니다. 항목을 더블클릭하면 해당 위치로 이동합니다. 오류 아이콘은 컴파일되지 않는 문제, 경고 아이콘은 컴파일은 되지만 예상과 다르게 동작할 수 있는 문제를 뜻합니다. 하나의 실수가 뒤따르는 오류를 여러 개 만들 수 있으니 보통 첫 오류부터 봅니다.

엔진 문서의 Keywords 페이지가 컴파일 단계에서 걸러진다고 설명하는 대표적인 경우는 다음과 같습니다.

| 원인 | 다시 볼 곳 |
|---|---|
| `override`한 메서드가 부모에 없거나 시그니처가 다름 | 6장 |
| `private`·`protected` 멤버를 바깥에서 사용 | 5장 |
| `sealed` 클래스를 상속하거나 `sealed` 메서드를 오버라이드 | 6장 |
| `const` 값을 바꿈 | 2장 |

엔진이 호출하는 이벤트 메서드를 오버라이드할 때 시그니처를 틀리는 실수가 특히 흔합니다. 기호 위에서 <Kbd>Ctrl</Kbd>+클릭으로 부모 클래스의 선언을 열어 그대로 복사하는 습관을 들이세요.

### 실행 중 오류: VME

실행 중에 처리되지 않은 문제가 생기면 <strong>VME(Virtual Machine Exception)</strong>가 발생합니다. 위키의 대표 예는 null 참조로 메서드를 호출하는 경우입니다. Workbench에서 VME가 나면 대화상자나 알림이 뜨고, 로그에 원인(`Reason:`)과 호출 스택(`Stack trace:`)이 남습니다. 대화상자 대신 다른 동작을 원하면 `-VMErrorMode`(`silent`, `log_only`, `full`, `fatal`)를 쓰고, `-noThrow`는 오류 대화상자를 모두 끕니다.

null 참조 VME의 원인은 대개 다음 가운데 하나입니다.

- `FindComponent()`가 null을 반환했다. 프리팹에 그 컴포넌트가 없다(10장).
- `Cast()`가 null을 반환했다. 실제 타입이 예상과 다르다(6장).
- 강한 참조가 없어 객체가 이미 해제되었다(7장).
- 클라이언트에 아직 스트리밍되지 않은 엔티티를 찾았다(14장).

`notnull` 매개변수에 null을 넘기면 위키 설명대로 VME가 발생하고 메서드는 호출되지 않습니다. null이 될 수 있는 값은 호출 전에 검사하고, 오류가 나면 `Debug.DumpStack()`이나 디버거의 **Callstack**으로 누가 그 값을 넘겼는지 거슬러 올라갑니다.

## 정리

<Summary>

- `Print`와 `PrintFormat`에 `LogLevel`을 주어 로그를 남깁니다. `PrintFormat`의 수준은 `level:` 이름 있는 인수로 넘깁니다.
- 로그는 Script Editor의 **Output** 창과 프로필 디렉터리의 `logs` 폴더에 남고, `-logLevel`, `-logsDir` 등으로 조절합니다.
- Script Editor 디버거는 <Kbd>F9</Kbd> 브레이크포인트, Step Over/Into/Out, Watch, Callstack, Remote Console을 제공합니다. 코드 안의 `debug;` 문도 브레이크포인트가 됩니다. 실제 클라이언트·서버는 Diag 실행 파일로 디버깅합니다.
- Diag Menu에는 스크립트 프로파일러, 느린 스크립트 로그, 사용자 액션 로그 같은 항목이 있고, `modded enum SCR_DebugMenuID`와 `DiagMenu`로 자기 항목을 추가할 수 있습니다.
- `Shape`와 `DebugTextWorldSpace`로 월드에 디버그 도형과 글자를 그립니다. `ONCE` 플래그는 매 프레임 다시 그리고, 그렇지 않으면 `ref`로 보관합니다.
- 성능은 "필요한가, 여기서인가, 이만큼인가, 지금인가, 이렇게 자주인가"로 점검합니다. 컴포넌트 검색 결과를 저장하고, 매 프레임 코드를 타이머로 바꾸는 것이 기본입니다.
- 자동 테스트는 `SCR_AutotestSuiteBase`와 `SCR_AutotestCaseBase`를 상속해 `[Test]`, `[TestStep]`으로 작성하고, Autotest 플러그인이나 `-autotest`로 실행합니다.
- 컴파일 오류는 **Errors** 창에서, 실행 중 오류는 VME 로그와 호출 스택에서 원인을 찾습니다.

</Summary>

<Exercise id="15-5" level="도전" title="테스트할 수 있게 계산 떼어 내기">

본문의 테스트가 쓰는 `TAG_SupplyMath` 클래스를 만드세요. 정적 메서드 `GetRemaining(int capacity, int taken)`은 남은 수량을 반환하되 0보다 작아지지 않아야 하고, `CanTake(int capacity, int taken)`은 하나 더 가져갈 수 있으면 `true`를 반환합니다. 그리고 `CanTake()`를 검사하는 테스트 케이스를 본문의 스위트에 하나 더 추가하세요.

</Exercise>
