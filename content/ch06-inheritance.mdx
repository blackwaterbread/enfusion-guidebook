<Objectives>

- `:`와 `extends`로 클래스를 상속하고, 부모 생성자가 호출되는 규칙을 설명할 수 있다.
- `override`와 `super`로 부모 메서드를 대체하거나 확장할 수 있다.
- 부모 타입 변수로 자식 객체를 다루는 다형성을 활용할 수 있다.
- `Cast`, `IsInherited`, `Type()`, `typename`으로 실행 중에 타입을 확인하고 안전하게 다운캐스트할 수 있다.
- 추상 클래스와 인터페이스가 없는 Enforce Script에서 공식 코드가 쓰는 관례를 따를 수 있다.

</Objectives>

Arma Reforger 스크립팅의 대부분은 이미 있는 클래스를 상속하는 일입니다. 스크립트 컴포넌트는 `ScriptComponent`를, 사용자 액션은 `ScriptedUserAction`을 상속하고, 엔진이 부르는 메서드를 오버라이드해 원하는 동작을 넣습니다. 공식 샘플의 `SCR_DrawerUserAction`도 `ScriptedUserAction`을 상속해 `PerformAction`을 오버라이드합니다.

## 상속 기본

### 문법: `:`와 extends

클래스 이름 뒤에 `:`와 부모 클래스 이름을 쓰면 상속합니다. `extends` 키워드를 써도 뜻은 같습니다. 공식 스크립트는 거의 모두 `:`를 쓰므로 이 책도 `:`를 씁니다. 부모 클래스는 **하나만** 지정할 수 있습니다.

```enforce
class TAG_Shotgun : TAG_Weapon
{
}

// 같은 뜻: class TAG_Shotgun extends TAG_Weapon
```

예제로 쓸 부모 클래스는 이름과 탄 수를 가진 무기입니다. `Fire()`는 탄이 있으면 하나를 줄이고 `OnFired()`를 부릅니다.

```enforce title="Scripts/Game/TAG_Weapon.c"
class TAG_Weapon
{
	protected string m_sName;
	protected int m_iAmmo;

	//------------------------------------------------------------------------------------------------
	void TAG_Weapon(string name, int ammo)
	{
		m_sName = name;
		m_iAmmo = ammo;
	}

	//------------------------------------------------------------------------------------------------
	string GetName()
	{
		return m_sName;
	}

	//------------------------------------------------------------------------------------------------
	void Fire()
	{
		if (m_iAmmo <= 0)
		{
			PrintFormat("%1: click", m_sName);
			return;
		}

		m_iAmmo--;
		OnFired();
	}

	//------------------------------------------------------------------------------------------------
	//! 발사에 성공한 뒤 호출됩니다. 자식 클래스가 오버라이드해 동작을 바꿉니다.
	protected void OnFired()
	{
		PrintFormat("%1: bang", m_sName);
	}
}
```

자식 클래스는 부모의 public 멤버와 `protected` 멤버를 물려받아 자기 것처럼 씁니다. 부모의 `private` 멤버는 자식 클래스 안에서도 쓸 수 없습니다.

```enforce title="Scripts/Game/TAG_Shotgun.c"
class TAG_Shotgun : TAG_Weapon
{
	protected int m_iPellets;

	//------------------------------------------------------------------------------------------------
	void TAG_Shotgun(string name, int ammo, int pellets)
	{
		m_iPellets = pellets;
	}

	//------------------------------------------------------------------------------------------------
	int GetPellets()
	{
		return m_iPellets;
	}
}
```

`TAG_Shotgun`에는 `Fire()`나 `GetName()`이 없지만 `shotgun.Fire()`처럼 부를 수 있습니다. 부모에게서 물려받았기 때문입니다.

### 부모 생성자는 자동으로 먼저 실행됩니다

`TAG_Shotgun`의 생성자는 `m_sName`과 `m_iAmmo`를 설정하지 않습니다. 그래도 `new TAG_Shotgun("Shotgun", 2, 8)`로 만든 객체의 이름은 "Shotgun"이고 탄은 2발입니다. 엔진 문서가 설명하듯 **부모 생성자는 자동으로 호출되기** 때문입니다. 이때 자식 생성자가 받은 인수 가운데 앞쪽 인수(`name`, `ammo`)가 부모 생성자로 전달되고, 부모 생성자가 끝난 뒤에 자식 생성자의 본문이 실행됩니다.

그래서 자식 생성자의 매개변수에는 규칙이 있습니다. 엔진 문서는 이를 "자식 클래스는 부모 생성자가 받는 인수에 새 인수를 **추가**할 수만 있다"고 표현합니다. 부모 생성자의 매개변수를 같은 순서로 앞에 두고, 그 뒤에 새 매개변수를 붙여야 합니다. 공식 스크립트에서도 `SCR_TimerEntryBase(string name)`를 상속한 `SCR_WorldTimerEntry`의 생성자는 `(string name, World world)`입니다.

자식 클래스가 생성자를 선언하지 않으면 부모 생성자의 매개변수를 그대로 씁니다. 공식 `SCR_RealTimerEntry`는 생성자 없이 `SCR_TimerEntryBase`를 상속하며, `new SCR_RealTimerEntry(timerName)`처럼 부모 생성자의 인수를 넘겨 만듭니다.

<Compare title="부모 생성자 호출">

```csharp
class Shotgun : Weapon
{
    int pellets;
    public Shotgun(string name, int ammo, int pellets) : base(name, ammo)
    {
        this.pellets = pellets;
    }
}
```

```javascript
class Shotgun extends Weapon {
  constructor(name, ammo, pellets) {
    super(name, ammo);
    this.pellets = pellets;
  }
}
```

```enforce
class TAG_Shotgun : TAG_Weapon
{
	protected int m_iPellets;

	// 앞의 두 인수가 자동으로 TAG_Weapon(name, ammo)에 전달됩니다
	void TAG_Shotgun(string name, int ammo, int pellets)
	{
		m_iPellets = pellets;
	}
}
```

</Compare>

C#의 `: base(...)`나 JavaScript의 `super(...)`처럼 부모 생성자를 직접 부르는 문법은 쓰지 않습니다. 대신 매개변수 순서로 무엇이 부모에게 갈지가 정해집니다.

<Pitfall title="자식 생성자의 매개변수 순서 바꾸기">

`void TAG_Shotgun(int pellets, string name, int ammo)`처럼 새 매개변수를 앞에 두면 부모 생성자의 매개변수가 앞에 와야 한다는 규칙을 어기게 됩니다. 부모 매개변수를 같은 순서·같은 타입으로 앞에 두고, 새 매개변수는 항상 뒤에 붙이세요. 공식 스크립트에서 생성자를 둔 자식 클래스도 이 형태를 따릅니다.

</Pitfall>

## 오버라이드와 super

### override

자식 클래스에서 부모의 메서드를 다시 정의하는 것을 **오버라이드**(override)라고 합니다. 엔진 문서에 따르면 Enforce Script의 멤버 함수는 모두 가상 함수라서 자식이 오버라이드할 수 있고, 오버라이드할 때는 반드시 `override` 키워드를 붙여야 합니다. 컴파일러는 부모에 같은 메서드가 있는지, 시그니처가 같은지 검사합니다.

```enforce
class TAG_Shotgun : TAG_Weapon
{
	// ...

	//------------------------------------------------------------------------------------------------
	override protected void OnFired()
	{
		PrintFormat("%1: boom (%2 pellets)", m_sName, m_iPellets);
	}
}
```

오버라이드하는 메서드는 부모 메서드와 시그니처가 **완전히** 같아야 합니다. 반환 타입과 매개변수 타입은 물론이고, 위키 문서에 따르면 **매개변수 이름까지** 같아야 합니다. 공식 스크립트의 오버라이드도 부모 선언과 같은 매개변수 이름을 씁니다. 부모 메서드를 복사해 와서 `override`만 붙이는 습관을 들이면 실수가 줄어듭니다.

```enforce
// 부모: int GetDamage(int distance, bool headshot)
override int GetDamage(int distance, bool headshot)  // OK
override int GetDamage(int distance, int headshot)   // 안 됨: 매개변수 타입이 다름
override int GetDamage(int range, bool headshot)     // 안 됨: 매개변수 이름이 다름
```

부모의 `private` 메서드는 오버라이드할 수 없습니다. public이나 `protected` 메서드만 오버라이드할 수 있습니다. 접근 제한자와 `override`의 순서는 자유로워서 공식 코드에도 `override protected`와 `protected override`가 모두 쓰입니다.

### super

오버라이드한 메서드 안에서 부모의 원래 동작이 필요하면 `super`로 부모 버전을 부릅니다. 부모의 동작을 그대로 둔 채 앞뒤에 일을 더하는 것을 흔히 **확장**이라고 합니다.

```enforce
override protected void OnFired()
{
	super.OnFired();                         // 부모의 "bang" 출력
	PrintFormat("%1 pellets", m_iPellets);   // 자식이 더한 동작
}
```

`super`는 바로 위 부모의 버전을 가리킵니다. 부모가 그 메서드를 다시 오버라이드했다면 부모가 정의한 버전이 실행됩니다. `super`를 부르지 않으면 부모의 동작을 완전히 **대체**합니다.

<Tip title="공식 클래스를 상속할 때는 super를 먼저 생각하기">

직접 만든 부모 클래스라면 부모가 무엇을 하는지 압니다. 하지만 공식 클래스의 메서드를 오버라이드할 때는 부모가 초기화나 이벤트 처리를 하고 있을 수 있습니다. 대체해야 할 분명한 이유가 없다면 `super`를 불러 부모의 동작을 살려 두세요. 공식 샘플 `SampleMod_ModdedScript`도 오버라이드한 메서드에서 먼저 `super.AddSuicide(playerId, count)`를 부른 뒤 동작을 더합니다.

</Tip>

<Compare title="가상 메서드와 오버라이드 표시">

```csharp
class Weapon { public virtual void OnFired() { } }
class Shotgun : Weapon { public override void OnFired() { base.OnFired(); } }
```

```python
class Shotgun(Weapon):
    def on_fired(self):  # 표시 없이 같은 이름으로 정의하면 오버라이드
        super().on_fired()
```

```enforce
class TAG_Shotgun : TAG_Weapon
{
	override protected void OnFired() // 부모에 virtual 표시는 필요 없음
	{
		super.OnFired();
	}
}
```

</Compare>

C#은 부모에 `virtual`, 자식에 `override`를 모두 적어야 합니다. Python과 JavaScript는 아무 표시도 하지 않습니다. Enforce Script는 그 중간입니다. 모든 메서드가 가상이므로 부모에는 표시가 없고, 자식에는 `override`가 필수입니다.

## 다형성

부모 타입 변수에는 자식 객체를 담을 수 있습니다. 그리고 그 변수로 메서드를 부르면 객체의 **실제 타입**에 맞는 버전이 실행됩니다. 이 성질을 **다형성**(polymorphism)이라고 합니다. 다음 예제는 권총과 산탄총을 한 배열에 담아 똑같이 `Fire()`를 부릅니다. 여기서 `TAG_Shotgun`은 앞의 `super` 예제처럼 `OnFired`를 확장한 버전입니다.

```enforce title="Scripts/Game/TAG_ArsenalDemo.c"
class TAG_ArsenalDemo
{
	static void Run()
	{
		array<ref TAG_Weapon> weapons = {};
		weapons.Insert(new TAG_Weapon("Pistol", 0));
		weapons.Insert(new TAG_Shotgun("Shotgun", 2, 8));

		foreach (TAG_Weapon weapon : weapons)
		{
			weapon.Fire();
		}
	}
}
```

실행 결과는 다음과 같습니다.

```text
Pistol: click
Shotgun: bang
8 pellets
```

`array<ref TAG_Weapon>`는 무기 객체를 담는 배열입니다. `ref`는 7장, 배열은 8장에서 설명합니다. 반복문의 `weapon` 변수 타입은 `TAG_Weapon`이지만, 두 번째 객체에서는 `TAG_Shotgun`이 오버라이드한 `OnFired`가 실행되었습니다. `Fire()`는 부모에 하나만 있고, 그 안에서 부르는 `OnFired()`만 자식마다 달라집니다.

이 구조는 공식 스크립트와 엔진이 쓰는 방식과 같습니다. `ScriptedUserAction`의 `PerformAction(IEntity pOwnerEntity, IEntity pUserEntity)`은 `event`로 선언된 메서드로, 사용자 액션이 실행될 때 엔진이 부릅니다. 여러분이 이 메서드를 오버라이드하면 엔진은 여러분의 버전을 실행합니다. 흐름은 부모(또는 엔진)가 정하고, 바뀌는 단계만 자식이 채우는 것입니다.

## sealed

`sealed`는 상속이나 오버라이드를 막는 키워드입니다. 클래스 앞에 붙이면 그 클래스를 상속할 수 없고, 메서드 앞에 붙이면 자식이 그 메서드를 오버라이드할 수 없습니다. 어기면 컴파일 오류가 납니다.

```enforce
sealed class TAG_Config
{
}

class TAG_Launcher
{
	sealed void Launch()
	{
		// 자식이 바꾸면 안 되는 흐름
	}
}
```

엔진이 제공하는 `string`, `vector`, `Math` 같은 클래스도 `sealed`로 선언되어 있어 상속할 수 없습니다. 공식 스크립트에서는 흐름을 고정해야 하는 메서드에 `sealed`를 씁니다. 예를 들어 `SCR_EffectModule`의 `OnModulePreExecute()`가 `sealed`입니다. 다만 `sealed`는 모드가 클래스를 확장할 여지도 줄이므로 꼭 필요한 곳에만 씁니다.

## 형변환과 타입 검사

### 업캐스트는 자동입니다

자식 객체를 부모 타입 변수에 담는 것을 **업캐스트**(upcast)라고 합니다. 산탄총은 무기이므로 별도 표시 없이 대입할 수 있습니다.

```enforce
TAG_Weapon weapon = new TAG_Shotgun("Shotgun", 2, 8); // 업캐스트
weapon.Fire();          // OK: TAG_Weapon의 메서드
weapon.GetPellets();    // 컴파일 오류: TAG_Weapon에는 GetPellets가 없음
```

변수의 타입이 `TAG_Weapon`이므로 컴파일러는 `TAG_Weapon`에 있는 멤버만 허용합니다. 실제 객체가 산탄총이어도 `GetPellets()`는 부를 수 없습니다.

### 다운캐스트는 Cast로

부모 타입으로 받은 객체를 자식 타입으로 다시 보는 것을 **다운캐스트**(downcast)라고 합니다. 모든 무기가 산탄총은 아니므로 자동으로 되지 않고, 반드시 `자식클래스.Cast(값)`으로 **형변환**(cast)해야 합니다. `Cast`는 객체가 그 타입(또는 그 자식 타입)이면 형변환한 값을, 아니면 `null`을 돌려줍니다. 예외를 던지지 않습니다.

```enforce
class TAG_WeaponInspector
{
	static void Inspect(TAG_Weapon weapon)
	{
		TAG_Shotgun shotgun = TAG_Shotgun.Cast(weapon);
		if (!shotgun)
		{
			PrintFormat("%1 is not a shotgun", weapon.GetName());
			return;
		}

		PrintFormat("%1 fires %2 pellets", shotgun.GetName(), shotgun.GetPellets());
	}
}
```

`Cast` 다음에는 언제나 null 검사가 따라옵니다. 이 두 줄짜리 관용구는 공식 스크립트에서 가장 많이 보는 코드 가운데 하나입니다. 특히 엔티티에서 컴포넌트를 찾을 때 자주 씁니다. `FindComponent`는 `Managed` 타입을 돌려주므로 원하는 컴포넌트 타입으로 형변환해야 합니다(10장).

```enforce
SCR_CharacterControllerComponent controller = SCR_CharacterControllerComponent.Cast(
	entity.FindComponent(SCR_CharacterControllerComponent));
if (!controller)
	return;
```

공식 코드는 null일 수 있는 값도 그대로 `Cast`에 넘기고 결과만 확인합니다. 위 코드에서 엔티티에 그 컴포넌트가 없으면 `FindComponent`가 null을 돌려주고, 형변환 결과인 `controller`도 null이 되어 같은 검사로 걸러집니다.

<Pitfall title="Cast 없이 자식 타입에 대입하기">

```enforce
TAG_Shotgun shotgun = weapon;                   // 잘못: 부모 타입을 그대로 대입
TAG_Shotgun shotgun2 = TAG_Shotgun.Cast(weapon); // 올바름
if (!shotgun2)
	return;
```

엔진 문서는 부모 타입 값을 자식 타입 변수에 바로 대입하는 코드를 오류로 설명합니다. 부모 타입은 "너무 일반적"이어서 실제로 자식인지 알 수 없기 때문입니다. 항상 `Cast`를 거치고 결과를 확인하세요.

</Pitfall>

### IsInherited와 Type

형변환한 객체를 쓸 필요 없이 "이 객체가 어떤 타입인가"만 알고 싶을 때는 `Class`에 정의된 메서드를 씁니다. 모든 객체에서 부를 수 있습니다.

| 메서드 | 반환 | 뜻 |
|---|---|---|
| `IsInherited(typename type)` | `bool` | 객체가 `type`이거나 그 자식 타입이면 `true` |
| `Type()` | `typename` | 객체의 실제 타입 |
| `ClassName()` | `string` | 객체의 실제 클래스 이름 |

```enforce
TAG_Weapon weapon = new TAG_Shotgun("Shotgun", 2, 8);

bool isWeapon = weapon.IsInherited(TAG_Weapon);   // true
bool isShotgun = weapon.IsInherited(TAG_Shotgun); // true
bool exactlyWeapon = weapon.Type() == TAG_Weapon; // false: 실제 타입은 TAG_Shotgun
string className = weapon.ClassName();            // "TAG_Shotgun"
```

`IsInherited`는 자식 타입까지 포함해 검사하고, `Type() ==` 비교는 정확히 그 타입인지 검사합니다. 공식 코드에도 두 형태가 모두 있습니다. 대부분의 경우에는 자식 클래스도 받아 주는 `IsInherited`나 `Cast`가 알맞습니다. `Type() ==`는 정확히 그 클래스만 골라야 할 때 씁니다.

### typename 활용

`typename`은 타입 자체를 값으로 담는 기본 타입입니다(2장). 클래스 이름을 그대로 쓰면 `typename` 값이 됩니다.

```enforce
typename shotgunType = TAG_Shotgun;
string name = shotgunType.ToString();            // "TAG_Shotgun"
typename fromName = "TAG_Shotgun".ToType();      // 문자열로 타입 찾기
bool related = fromName.IsInherited(TAG_Weapon); // true
```

`string`의 `ToType()`은 이름에 맞는 타입이 없으면 빈 값(`typename.Empty`)을 돌려줍니다. `typename`의 `Spawn()`은 `new`의 동적 버전으로, 그 타입의 객체를 만들어 `ref Managed` 타입으로 돌려줍니다. 인수를 넘길 방법이 없으므로 인수 없이 만들 수 있는 클래스에 씁니다. 다음은 설정 파일 등에서 읽은 클래스 이름으로 객체를 만드는 팩토리입니다.

```enforce title="Scripts/Game/TAG_OrderFactory.c"
class TAG_OrderBase
{
	string GetLabel()
	{
		return "order";
	}
}

class TAG_MoveOrder : TAG_OrderBase
{
	override string GetLabel()
	{
		return "move";
	}
}

class TAG_OrderFactory
{
	static TAG_OrderBase CreateByName(string className)
	{
		typename orderType = className.ToType();
		if (!orderType || !orderType.IsInherited(TAG_OrderBase))
			return null;

		return TAG_OrderBase.Cast(orderType.Spawn());
	}
}
```

`TAG_OrderFactory.CreateByName("TAG_MoveOrder")`는 `TAG_MoveOrder` 객체를 돌려주고, 없는 이름이나 관계없는 클래스 이름에는 null을 돌려줍니다. 공식 스크립트도 `SCR_TaskSolverBase.Cast(solverType.Spawn())`처럼 같은 방식으로 객체를 만듭니다. `typename`이 비었는지는 `!orderType`이나 `orderType == typename.Empty`로 확인합니다.

## Class와 Managed

Enforce Script의 모든 클래스는 `Class`를 뿌리로 합니다. 공식 정의(`Core/proto/Types.c`)는 `Class`를 "모든 클래스의 최상위 부모"로 설명하며, 앞에서 쓴 `IsInherited`, `Type`, `ClassName`, `Cast`가 여기에 정의되어 있습니다. 그래서 어떤 클래스의 객체든 이 메서드들을 쓸 수 있습니다.

`Managed`는 상속한 클래스의 객체를 엔진의 **자동 참조 카운팅**(ARC) 대상으로 만드는 부모 클래스입니다. 엔진 문서에 따르면 `Managed`를 상속한 클래스의 객체는 참조 수가 0이 되면 자동으로 파괴되고, 그 객체를 가리키던 약한 참조는 `null`이 됩니다. `array`, `set`, `map`, 엔티티의 부모인 `IEntity`, UI의 `Widget` 같은 주요 엔진 클래스가 `Managed`를 상속합니다.

직접 만드는 클래스에 `: Managed`를 적어야 하는지, 참조가 객체의 수명을 어떻게 정하는지는 7장에서 자세히 다룹니다.

## 추상 클래스와 인터페이스 대신 쓰는 관례

Enforce Script에는 `abstract`나 `interface` 키워드가 없습니다. 그래서 공식 스크립트는 다음 관례로 "직접 만들지 않고 상속해서 쓰는 클래스"를 표현합니다.

- **이름에 `Base`를 붙인 부모 클래스**를 둡니다. `SCR_AIActivityBase`, `SCR_TimerEntryBase`, `SCR_BTParamBase`가 그런 예입니다.
- 자식이 반드시 구현해야 하는 메서드는 **본문 없이 선언**합니다. `SCR_TimerEntryBase`는 `void SetTimer(float seconds);`처럼 선언만 하고, `SCR_AICombatMoveLogicBase`에는 "이 메서드들은 자식 클래스에서 반드시 오버라이드해야 한다"는 주석과 함께 본문 없는 선언이 모여 있습니다.
- 기본 동작이 있는 메서드는 **본문을 둡니다**. `ScriptedUserAction`의 `CanBePerformedScript`는 기본으로 `true`를 반환하고, 필요한 자식만 오버라이드합니다.
- 직접 만들지 못하게 하려면 **생성자를 `protected`로** 둡니다. 공식 `AnimPhysCommandScripted`에는 "이 '추상' 클래스의 인스턴스를 원하지 않으므로 생성자를 protected로 둔다"는 주석이 달려 있습니다. 단, 부모 생성자가 `protected`이면 `typename.Spawn()`은 그 클래스를 상속한 자식 타입도 만들지 못하고 null을 돌려줍니다. 클래스 이름으로 객체를 만들어야 하는 계층에서는 생성자를 `protected`로 두지 않습니다.

이 관례를 따른 예제입니다.

```enforce title="Scripts/Game/TAG_InteractionBase.c"
//! 상호작용의 공통 부모입니다. 직접 만들지 않고 상속해서 씁니다.
class TAG_InteractionBase
{
	//------------------------------------------------------------------------------------------------
	protected void TAG_InteractionBase()
	{
	}

	//------------------------------------------------------------------------------------------------
	//! 자식 클래스가 반드시 오버라이드합니다.
	string GetActionName();

	//------------------------------------------------------------------------------------------------
	//! 기본 동작이 있으므로 필요할 때만 오버라이드합니다.
	bool CanInteract(int playerLevel)
	{
		return true;
	}
}

class TAG_OpenDoorInteraction : TAG_InteractionBase
{
	//------------------------------------------------------------------------------------------------
	void TAG_OpenDoorInteraction()
	{
	}

	//------------------------------------------------------------------------------------------------
	override string GetActionName()
	{
		return "Open door";
	}
}
```

부모의 생성자가 `protected`이므로 바깥에서 `new TAG_InteractionBase()`는 쓸 수 없습니다. 자식 클래스에는 public 생성자를 두었으므로 `new TAG_OpenDoorInteraction()`으로 만들 수 있습니다. 공식 `ScriptedCommand`도 생성자가 `protected`이고, 이를 상속한 `SCR_CharacterCommandFly`는 public 생성자를 두어 `new`로 만듭니다.

본문 없는 메서드는 "자식이 구현할 자리"라는 표시입니다. 이 메서드를 오버라이드하지 않은 채 호출했을 때 어떻게 되는지는 문서에 나와 있지 않습니다. 자식이 구현하지 않아도 되는 메서드라면 위의 `CanInteract`처럼 기본 본문을 두세요.

다른 언어의 인터페이스처럼 "이 기능을 가진 객체인가"를 확인해야 할 때도 공통 부모 클래스를 둡니다. 객체를 받는 쪽에서 `TAG_InteractionBase.Cast(obj)`로 형변환해 보고, null이 아니면 그 기능을 쓰는 방식입니다.

## modded 클래스 미리 보기

상속은 새 클래스를 만듭니다. 반면 `modded class`는 이미 있는 클래스를 **그 자리에서** 고칩니다. modded 클래스는 원래 클래스를 상속한 것처럼 동작하지만, 게임 전체에서 원래 클래스 대신 쓰입니다. 그래서 공식 클래스의 동작을 바꾸는 모드의 핵심 도구입니다.

```enforce
modded class SCR_BaseGameMode
{
	override void OnPlayerConnected(int playerId)
	{
		super.OnPlayerConnected(playerId); // 원래 동작
		PrintFormat("TAG: player %1 connected", playerId);
	}
}
```

문법은 이 장에서 배운 오버라이드와 같습니다. `override`로 메서드를 다시 정의하고 `super`로 원래 동작을 부릅니다. 여러 모드가 같은 클래스를 고칠 때의 순서, 새 멤버에 태그를 붙이는 규칙 같은 자세한 내용은 12장에서 다룹니다.

## 정리

<Summary>

- `class 자식 : 부모`(또는 `extends`)로 상속합니다. 부모는 하나만 둘 수 있고, 자식은 부모의 public·`protected` 멤버를 물려받습니다.
- 부모 생성자는 자동으로 먼저 실행됩니다. 자식 생성자는 부모 생성자의 매개변수를 같은 순서로 앞에 두고 새 매개변수를 뒤에 붙입니다. 생성자가 없는 자식은 부모 생성자의 매개변수를 씁니다.
- 모든 메서드는 가상 함수이고, 오버라이드할 때는 `override`가 필수입니다. 반환 타입, 매개변수 타입, 매개변수 이름까지 부모와 같아야 합니다.
- `super.메서드()`로 부모의 동작을 부를 수 있습니다. 공식 클래스를 상속할 때는 대체할 이유가 없다면 `super`를 부릅니다.
- 부모 타입 변수로 자식 객체를 다루면 실제 타입의 오버라이드가 실행됩니다. 흐름은 부모가 정하고 바뀌는 단계만 자식이 채우는 구조가 엔진과 공식 코드의 기본 패턴입니다.
- 다운캐스트는 `자식클래스.Cast(값)`으로 하고, 결과가 null인지 반드시 확인합니다. 타입만 확인할 때는 `IsInherited`, 정확한 타입 비교는 `Type() ==`를 씁니다.
- `typename`으로 타입을 값처럼 다룰 수 있습니다. `ToType()`으로 이름에서 타입을 찾고, `Spawn()`으로 객체를 만든 뒤 `Cast`합니다.
- `abstract`와 `interface`가 없으므로 `Base` 부모 클래스, 본문 없는 메서드 선언, 기본 본문, `protected` 생성자로 같은 효과를 냅니다.

</Summary>
