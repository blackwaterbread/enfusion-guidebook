<Objectives>

- 서버, 클라이언트, 리슨 서버, 데디케이티드 서버의 차이를 설명할 수 있다.
- 권한자(Authority), 프록시(Proxy), 소유자(Owner)를 구분하고 `RplComponent`로 지금 실행 중인 쪽의 역할을 확인할 수 있다.
- `[RplProp]`과 `Replication.BumpMe()`로 상태를 복제하고, 값이 바뀔 때 콜백을 받을 수 있다.
- `[RplRpc]`와 `Rpc()`로 원격 프로시저 호출을 보내고, 수신자에 따라 어디서 실행되는지 표로 판단할 수 있다.
- 엔티티 생성·삭제, 계층 구조, 스트리밍이 리플리케이션에 주는 제약을 설명할 수 있다.

</Objectives>

지금까지 만든 컴포넌트는 모두 한 컴퓨터 안에서만 돌았습니다. Arma Reforger는 여러 플레이어가 같은 월드를 공유하는 게임이므로, 실제 모드는 거의 언제나 멀티플레이어에서 동작해야 합니다. 같은 스크립트가 서버와 여러 클라이언트에서 동시에 실행되는데, 어느 기계가 상태를 결정하고 그 결과를 누구에게 어떻게 전달할지 정해 주는 것이 리플리케이션(Replication) 시스템입니다.

이 장은 리플리케이션의 개념과 스크립트 API를 다룹니다. 엔티티와 컴포넌트는 10장에서 설명했습니다. 여기서 배운 내용은 16장 실전 프로젝트에서 그대로 씁니다.

## 서버와 클라이언트

Enfusion 엔진의 네트워크는 서버-클라이언트 구조입니다. 세션에는 서버가 정확히 하나 있고, 클라이언트는 서버하고만 통신합니다. 서버는 게임 시뮬레이션의 권한을 쥐고 있는 "정답의 원천(source of truth)"이며, 각 클라이언트가 무엇을 알고 무엇을 할 수 있는지도 서버가 정합니다.

서버가 사라지면 세션이 끝나고 클라이언트의 연결도 끊깁니다. 다른 클라이언트가 서버 역할을 이어받는 기능은 없습니다.

### 리슨 서버, 데디케이티드 서버, 싱글플레이

서버를 여는 방식은 두 가지입니다.

- **리슨 서버(listen server)**: 플레이어 한 명이 서버를 겸합니다. 그 플레이어의 키보드·마우스 입력을 직접 받고 화면과 소리도 그 플레이어에게 출력합니다.
- **데디케이티드 서버(dedicated server)**: 입력도 화면 출력도 없이 서버 역할만 합니다. 플레이어는 모두 원격으로 접속합니다.

싱글플레이는 "클라이언트 접속을 받지 않는 리슨 서버"로 생각하면 됩니다. 공식 문서도 같은 관점을 취하며, 제대로 설계한 멀티플레이어 코드는 싱글플레이에서도 그대로 동작해야 한다고 강조합니다.

현재 세션이 어떤 방식인지는 `RplSession.Mode()`가 `RplMode` 열거형으로 알려 줍니다. 값은 `None`, `Client`, `Listen`, `Dedicated` 네 가지입니다. 1.8.0.13 Workbench에서 확인해 보면 편집 모드와, Play 메뉴의 **Server localhost**를 켜지 않은 Play 모드 모두 `RplSession.Mode()`는 `None`이었고, `Replication.IsServer()`는 true였습니다. **Server localhost**를 켜고 Play하면 Workbench가 서버를 띄우므로 `Listen`이 됩니다. 다만 뒤에서 보듯이 이 값으로 코드를 나누는 일은 되도록 피합니다.

이 장의 예제를 클라이언트와 함께 시험하려면 공식 스크립트에 들어 있는 World Editor 플러그인 **Peer Tool**(`WorkbenchGameCommon/PeerTool.c`)을 씁니다(16장). 플러그인 설정의 **Executable**에 게임의 Diag 실행 파일(`ArmaReforgerSteamDiag.exe`) 경로를 넣고 피어 구성을 정해 둔 뒤, World Editor에서 Play 버튼 옆 목록의 **Server localhost + PeerTool**로 게임을 시작하면 Workbench에서 실행한 게임이 서버가 되고 피어 클라이언트들이 여기에 접속합니다. **Launch Delay**(초)로 피어 실행을 늦추면 이미 진행 중인 게임에 들어오는 중도 참가도 시험할 수 있습니다.

### 시뮬레이션과 프레젠테이션

엔진 문서는 게임 코드를 두 부분으로 나눠 생각하라고 권합니다.

- **시뮬레이션(simulation)**: 피해 계산, 체력 관리, AI 판단, 승리 조건 판정처럼 "보이지 않는 곳"에서 일어나는 게임 로직입니다.
- **프레젠테이션(presentation)**: 시뮬레이션 결과를 플레이어가 보고 들을 수 있게 만드는 부분입니다.

멀티플레이어 세션에서 시뮬레이션은 한 기계(서버)만 하고, 프레젠테이션은 모든 플레이어가 합니다. 리플리케이션의 주된 일은 시뮬레이션 결과 가운데 프레젠테이션에 꼭 필요한 데이터만 골라 플레이어들에게 전달하는 것입니다. 데디케이티드 서버에서는 렌더링과 오디오 같은 비싼 프레젠테이션이 자동으로 생략됩니다.

<Compare title="웹 서비스와 Enfusion 리플리케이션">

웹에서는 서버 코드와 브라우저 코드를 따로 작성하고 HTTP나 웹소켓으로 메시지를 주고받습니다.

```javascript
// 서버(Node.js): 상태를 가진 쪽
let running = false;
app.post('/generator/toggle', (req, res) => {
  running = !running;
  broadcastToBrowsers({ running }); // 웹소켓으로 모든 브라우저에 알림
  res.sendStatus(200);
});

// 브라우저: 요청만 보낸다
fetch('/generator/toggle', { method: 'POST' });
```

Enfusion에서는 같은 클래스가 서버와 모든 클라이언트에서 실행됩니다. 메시지 형식이나 주소를 직접 다루지 않고, 어트리뷰트로 "이 변수는 복제한다", "이 메서드는 서버에서 실행한다"고 표시합니다.

```enforce
[ComponentEditorProps(category: "TAG/Tutorial", description: "켜고 끌 수 있는 발전기")]
class TAG_GeneratorComponentClass : ScriptComponentClass
{
}

class TAG_GeneratorComponent : ScriptComponent
{
	// 서버에서 바꾸면 클라이언트로 복제되고, 클라이언트에서는 OnRunningChanged가 불린다
	[RplProp(onRplName: "OnRunningChanged")]
	protected bool m_bRunning;

	// 소유자가 Rpc()로 부르면 서버에서 실행된다
	[RplRpc(RplChannel.Reliable, RplRcver.Server)]
	protected void RpcAsk_Toggle()
	{
		m_bRunning = !m_bRunning;
		Replication.BumpMe();
	}

	protected void OnRunningChanged()
	{
		// 바뀐 값에 맞춰 소리나 화면을 바꾼다
	}
}
```

</Compare>

## 리플리케이션의 단위: 아이템, 노드, RplComponent

### 아이템과 노드

리플리케이션이 다루는 가장 작은 단위는 <strong>아이템(item)</strong>입니다. 대개 엔티티나 컴포넌트가 아이템이 되는데, 모든 엔티티와 컴포넌트가 아이템인 것은 아닙니다. 다음 가운데 하나 이상을 가진 것만 아이템으로 등록됩니다.

- 복제되는 속성(`[RplProp]`이 붙은 멤버 변수)
- RPC로 호출할 수 있는 메서드(`[RplRpc]`가 붙은 메서드)
- 리플리케이션 콜백

아이템 여러 개는 <strong>노드(node)</strong>로 묶여 리플리케이션에 등록됩니다. 노드가 한번 등록되면 그 안의 아이템 목록은 바꿀 수 없습니다. 노드끼리는 부모-자식 관계를 이루며, 이 관계는 등록 뒤에도 바꿀 수 있습니다. 캐릭터가 차량에 타는 상황처럼 엔티티 계층이 실행 중에 바뀌는 경우가 여기에 해당합니다.

또 하나 중요한 규칙이 있습니다. **서버에서 만든 아이템만 클라이언트와 공유됩니다.** 클라이언트에서 만든 아이템은 그 클라이언트에만 존재하고, 서버를 포함한 누구도 그 존재를 모릅니다.

### RplComponent

엔티티와 컴포넌트를 리플리케이션에 연결해 주는 것이 `RplComponent`입니다. 엔티티에 `RplComponent`를 붙이면, 초기화 중에(`EOnInit`) 그 엔티티와 컴포넌트 가운데 아이템이 될 수 있는 것을 모아 노드를 만들고 리플리케이션에 등록합니다. 위키도 "복제할 엔티티에는 언제나 `RplComponent`가 있어야 한다"고 적고 있습니다.

<Note title="BaseRplComponent와 RplComponent">

엔진 문서의 예제는 게임과 무관하게 쓰려고 `BaseRplComponent`(`GameLib/generated/Components/BaseRplComponent.c`)를 사용합니다. Arma Reforger에서는 이를 상속한 `RplComponent`(`Game/generated/Components/RplComponent.c`)를 쓰면 됩니다. 이 장의 예제도 `RplComponent`를 씁니다.

</Note>

## 역할: 권한자, 프록시, 소유자

### 권한자와 프록시

아이템이 리플리케이션에 등록되면 역할(`RplRole`)을 하나 받습니다.

- **권한자(Authority)**: 모든 기계를 통틀어 정확히 한 인스턴스만 권한자입니다. 상태의 정답을 갖고, 그 상태를 프록시에 복제합니다.
- **프록시(Proxy)**: 권한자를 제외한 나머지 인스턴스입니다. 권한자가 보내 주는 상태를 받기만 합니다.

서버에서 만든 엔티티는 서버의 인스턴스가 권한자이고, 각 클라이언트에는 프록시가 생깁니다. 클라이언트에서 만든 엔티티는 그 클라이언트의 인스턴스가 권한자가 되지만, 서버가 모르므로 어디에도 복제되지 않습니다. 권한자의 위치는 한번 정해지면 바뀌지 않습니다.

### 소유자

<strong>소유자(Owner)</strong>는 권한자·프록시와 별개로 붙는 성질입니다. 한 아이템을 두고 서버와 이야기할 수 있는 클라이언트는 많아야 하나이며, 그 클라이언트가 소유자입니다. 소유자는 그 아이템의 RPC로 서버에 요청을 보낼 수 있습니다. 서버는 원할 때 소유권을 클라이언트에 넘기거나(`RplComponent.Give()`) 되찾을 수 있고, 소유권을 넘기지 않은 아이템은 서버 자신이 소유합니다.

위키가 드는 예로, 플레이어가 차량의 운전석에 타면 서버는 그 차량의 소유권을 플레이어의 기계에 넘기고, 내리면 되찾습니다. 그동안에도 권한자는 계속 서버입니다. **소유권을 넘기는 것은 권한을 넘기는 것과 다릅니다.**

### 코드에서 역할 확인하기

`RplComponent`(정확히는 부모인 `BaseRplComponent`)에는 역할을 묻는 메서드가 있습니다.

| 메서드 | 반환 | 의미 |
|---|---|---|
| `Role()` | `RplRole` | `RplRole.Authority` 또는 `RplRole.Proxy` |
| `IsProxy()` | `bool` | 프록시이면 true |
| `IsOwner()` | `bool` | 이 기계가 소유자이면 true |
| `IsMaster()` | `bool` | 소유자이면서 권한자(`IsOwner() && !IsProxy()`) |
| `IsOwnerProxy()` | `bool` | 소유자이면서 프록시(`IsOwner() && IsProxy()`) |
| `IsRemoteProxy()` | `bool` | 소유자가 아닌 프록시(`!IsOwner() && IsProxy()`) |

"서버에서만 할 일"은 대부분 "권한자에서만 할 일"이므로 `Role() == RplRole.Authority` 또는 `!IsProxy()`로 확인합니다. `IsMaster()`는 소유자이기까지 해야 true이므로, 서버가 소유권을 클라이언트에 넘긴 엔티티에서는 서버에서도 false가 됩니다. 둘을 헷갈리지 않도록 주의하세요.

다음은 엔진 문서의 예제처럼, 매 프레임 시뮬레이션을 권한자에서만 돌리도록 이벤트 마스크를 거는 코드입니다. `BaseRplComponent`의 공식 주석에 따르면 역할과 소유권은 생성 시점부터 정확하므로 `OnPostInit`에서 확인해도 됩니다.

```enforce
override void OnPostInit(IEntity owner)
{
	RplComponent rpl = RplComponent.Cast(owner.FindComponent(RplComponent));
	if (!rpl)
	{
		Print("이 컴포넌트에는 RplComponent가 필요합니다.", LogLevel.WARNING);
		return;
	}

	// 시뮬레이션은 권한자만 한다. 프록시는 복제된 값에 반응만 한다.
	if (rpl.Role() == RplRole.Authority)
		SetEventMask(owner, EntityEvent.FRAME);
}
```

### "서버인가?"라고 묻지 않기

`Replication` 클래스에는 `IsServer()`와 `IsClient()`도 있습니다. 하지만 공식 소스는 두 메서드에 "하드코딩된 판단은 다른 환경에 적응하지 못하니 리플리케이션 역할과 소유권을 쓰라"는 경고 주석을 달아 두었습니다.

같은 코드가 싱글플레이, 리슨 서버, 데디케이티드 서버, 클라이언트라는 네 환경에서 돌기 때문입니다. "서버인가"로 나누면 리슨 서버의 호스트처럼 서버이면서 플레이어인 경우를 놓치기 쉽습니다. "이 엔티티의 권한자인가", "소유자인가"로 나누면 환경이 바뀌어도 규칙이 그대로 맞습니다. 공식 스크립트의 `Game/Network/RplTestComponent.c`와 `RplTestComponentWrong.c`가 옳은 방식과 잘못된 방식을 나란히 보여 주니 함께 읽어 보세요.

| 알고 싶은 것 | 사용할 API |
|---|---|
| 이 엔티티의 권한자인가 | `rpl.Role() == RplRole.Authority` 또는 `!rpl.IsProxy()` |
| 이 엔티티의 소유자인가 | `rpl.IsOwner()` |
| 세션 방식 | `RplSession.Mode()` (`RplMode.None`, `Client`, `Listen`, `Dedicated`) |
| 이 기계의 플레이어 | `SCR_PlayerController.GetLocalPlayerId()`, `SCR_PlayerController.GetLocalControlledEntity()` |

`GetLocalPlayerId()`는 로컬 `PlayerController`가 없으면 0을 반환하고, `GetLocalControlledEntity()`는 null을 반환합니다. UI처럼 "이 기계 앞에 앉은 플레이어"에게만 해당하는 일은 이 두 메서드로 판단합니다.

## 상태 복제: RplProp과 BumpMe

### 선언하고 바꾸기

권한자의 멤버 변수를 프록시로 복제하려면 `[RplProp]` 어트리뷰트를 붙입니다. 그리고 값을 바꾼 뒤 `Replication.BumpMe()`를 호출해 "복제할 변경이 있다"고 알립니다. 리플리케이션은 등록된 모든 아이템을 스스로 검사하지 않으므로 `BumpMe()`를 빠뜨리면 값이 전달되지 않습니다.

`BumpMe()`는 인수가 없는 정적 메서드입니다. 공식 코드에서 이 메서드는 복제 속성을 가진(또는 부모 클래스에서 물려받은) 객체 자신의 메서드 안에서 호출됩니다. 이 책도 그 방식을 따릅니다.

다음은 켜고 끌 수 있는 발전기 컴포넌트입니다. 이 장의 나머지 예제도 이 컴포넌트를 바탕으로 합니다.

```enforce title="Scripts/Game/TAG_GeneratorComponent.c"
[ComponentEditorProps(category: "TAG/Tutorial", description: "켜고 끌 수 있는 발전기")]
class TAG_GeneratorComponentClass : ScriptComponentClass
{
}

class TAG_GeneratorComponent : ScriptComponent
{
	[RplProp(onRplName: "OnRunningChanged")]
	protected bool m_bRunning;

	protected RplComponent m_RplComponent;

	override void OnPostInit(IEntity owner)
	{
		m_RplComponent = RplComponent.Cast(owner.FindComponent(RplComponent));
	}

	//! 권한자에서만 상태를 바꾼다. 프록시에서 부르면 아무 일도 하지 않는다.
	void SetRunning(bool running)
	{
		if (!m_RplComponent || m_RplComponent.IsProxy())
			return;

		if (m_bRunning == running)
			return;

		m_bRunning = running;
		Replication.BumpMe();	// 변경을 리플리케이션에 알린다
		OnRunningChanged();		// 권한자에서는 콜백이 자동으로 불리지 않는다
	}

	bool IsRunning()
	{
		return m_bRunning;
	}

	//! 프록시에서는 복제된 값이 들어온 뒤 자동으로 호출된다.
	protected void OnRunningChanged()
	{
		if (m_bRunning)
			Print("발전기가 켜졌습니다.");
		else
			Print("발전기가 꺼졌습니다.");
	}
}
```

이 컴포넌트를 쓰려면 엔티티에 `RplComponent`도 함께 붙여야 합니다. `m_bRunning`에 `[RplProp]`이 있으므로 이 컴포넌트는 아이템이 되고, `RplComponent`가 만든 노드에 들어갑니다.

### 값이 바뀔 때 콜백 받기

`onRplName`에는 메서드 이름을 문자열로 적습니다. 그 이름의 메서드가 없으면 컴파일 오류(``OnRpl callback method `TAG_GeneratorComponent.OnRunningChanged` does not exist.``)가 납니다. 리플리케이션이 프록시의 값을 갱신하면 그 메서드가 불립니다. 위키에 따르면 중도 참가(JIP)한 클라이언트가 처음 상태를 받을 때도 불립니다. 1.8.0.13에서 시험해 보면, 서버가 한 번도 바꾸지 않아 처음 값 그대로인 속성은 중도 참가 때 콜백이 불리지 않았습니다. 콜백은 매개변수가 없는 메서드이고, 불리는 시점에는 이미 새 값이 변수에 들어 있습니다.

**이 콜백은 권한자에서는 불리지 않습니다.** 그래서 위 예제의 `SetRunning()`은 값을 바꾼 뒤 `OnRunningChanged()`를 직접 호출합니다. 이렇게 하면 프레젠테이션 코드를 한 메서드에 모아 두고 권한자와 프록시가 같은 코드를 쓸 수 있습니다.

공식 테스트 컴포넌트의 주석은 프록시에서 이전 값을 따로 저장해 두고 매 프레임 비교하는 방식을 "잘못된 방법"으로 꼽습니다. 값 변화에는 콜백으로 반응하세요.

### 복제 조건

`RplProp`의 생성자(`Core/proto/EnNetwork.c`)는 `group`, `onRplName`, `ctx`, `condition`, `customConditionName` 순서의 매개변수를 받습니다. 첫 매개변수 `group`은 더 이상 쓰지 않으므로, 공식 코드처럼 이름 있는 인수로 필요한 것만 지정합니다. `condition`으로는 누구에게 보낼지를 좁힐 수 있습니다.

| `RplCondition` | 받는 대상 |
|---|---|
| `None` | 역할 규칙에 따라 관련된 모두(기본값) |
| `OwnerOnly` | 소유자에게만 |
| `NoOwner` | 소유자를 뺀 모두 |
| `Custom` | `customConditionName`에 적은 메서드가 true를 반환할 때 |

`Custom` 조건 메서드는 `bool`을 반환하는 멤버 메서드입니다. 엔진 문서는 "상대편에서 더는 필요 없는 값을 거를 때 쓰는 것이며, 특정 접속(클라이언트)을 골라내는 데는 쓸 수 없다"고 못 박고 있습니다.

```enforce
[RplProp(condition: RplCondition.OwnerOnly)]
protected int m_iPrivateAmmo;		// 소유자만 알면 되는 값

[RplProp(condition: RplCondition.Custom, customConditionName: "ShouldSendFuel")]
protected float m_fFuel;

protected bool ShouldSendFuel()
{
	return m_bRunning;	// 발전기가 꺼져 있으면 연료량을 보낼 필요가 없다
}
```

### 복제할 수 있는 타입과 주의점

공식 스크립트에서 `[RplProp]` 변수의 타입은 `int`, `bool`, `float`, `vector`, `string`, 열거형, `WorldTimestamp`, `RplId`와 `ref array<int>`, `ref array<RplId>` 같은 배열입니다. 직접 만든 클래스를 복제 속성이나 RPC 인수로 쓰려면 코덱(codec)이라 부르는 정적 메서드 묶음(`Extract`, `Inject`, `Encode`, `Decode`, `SnapCompare`, `PropCompare`)을 구현해야 합니다. 이 책에서는 다루지 않으며, 엔진 문서도 RPC 하나에만 쓰는 타입이라면 기본 타입 인수 여러 개로 나누는 편을 권합니다.

<Warning title="주입은 언제나 새 값으로 덮어씁니다">

프록시에 값을 넣는 과정(주입, injection)은 언제나 변수에 새 값을 씁니다. 문자열·배열·클래스 같은 복합 타입이면 새 인스턴스의 참조가 이전 참조를 덮어씁니다. 프록시에서 이전 배열에 따로 붙여 둔 데이터가 있었다면 사라집니다. 프록시는 복제 속성을 "읽기 전용"으로 다루세요.

</Warning>

## RPC: 원격 프로시저 호출

상태 복제는 "권한자의 값을 프록시에 맞추는" 한 방향 흐름입니다. 클라이언트가 서버에 무언가를 요청하거나, 서버가 특정 순간에 일어난 일을 알리려면 RPC(원격 프로시저 호출)를 씁니다.

### 선언과 호출

RPC로 부를 메서드에는 `[RplRpc]` 어트리뷰트를 붙입니다. 생성자는 `RplRpc(RplChannel channel, RplRcver rcver, RplCondition condition = RplCondition.None, string customConditionName = "")`입니다.

```enforce
[RplRpc(RplChannel.Reliable, RplRcver.Server)]
protected void RpcAsk_SetRunning(bool running)
{
	// 서버에서 실행된다
}
```

호출할 때는 메서드를 직접 부르지 않고 `Rpc()`에 메서드와 인수를 넘깁니다.

```enforce
Rpc(RpcAsk_SetRunning, true);
```

`Rpc()`는 `GenericEntity`와 `GenericComponent`에 `protected`로 선언된 메서드입니다. 시그니처는 `Rpc(func method, void p0 = NULL, ..., void p7 = NULL)`이므로 인수는 8개까지 넘길 수 있습니다. `protected`이기 때문에 다른 객체의 RPC를 바깥에서 대신 보낼 수는 없고, RPC를 가진 클래스 안에서 호출해야 합니다. 위키는 초기화 순서 문제 때문에 `EOnInit`에서 RPC를 호출하는 것은 지원하지 않는다고 적고 있습니다.

`Rpc()`를 거치지 않고 메서드를 그냥 호출하면 평범한 메서드 호출이 됩니다. 이 점을 이용해 "여기서도 실행하고 다른 곳으로도 보내는" 코드를 짤 수 있는데, 뒤의 브로드캐스트 절에서 다시 봅니다.

이름은 공식 관례를 따릅니다. 원격 호출용 메서드에는 `Rpc_` 접두사를 붙이고, 그 가운데 소유자가 권한자에게 요청하는 것은 `RpcAsk_`, 권한자가 소유자나 프록시에게 실행시키는 것은 `RpcDo_`로 시작합니다.

### 채널과 수신자, 라우팅 표

`RplChannel`은 두 가지입니다. `Reliable`은 전달이 보장되고, `Unreliable`은 보장되지 않습니다. 엔진 문서의 예제처럼 매 프레임 보내는 입력 상태 같은 것은 `Unreliable`로, 한 번만 보내는 요청은 `Reliable`로 보냅니다.

`RplRcver`는 메서드 본문이 실행될 곳을 고릅니다.

| `RplRcver` | 의미 |
|---|---|
| `Server` | 서버 쪽 |
| `Owner` | 인스턴스의 소유자 |
| `Broadcast` | 프록시 역할인 인스턴스들 |

실제로 어디서 실행되는지는 호출한 기계의 모드와 소유 여부에 따라 달라집니다. 다음 표는 `Core/generated/Replication/RplRcver.c`의 주석에 실린 라우팅 표를 옮긴 것입니다.

| 호출한 쪽 | 호출한 쪽이 소유자인가 | `Server` | `Owner` | `Broadcast` |
|---|---|---|---|---|
| 서버 | 예 | 서버에서 직접 실행 | 서버에서 직접 실행 | 관련 클라이언트로 전송 |
| 서버 | 아니요 | 서버에서 직접 실행 | 소유자 클라이언트로 전송 | 관련 클라이언트로 전송 |
| 클라이언트 | 예 | 서버로 전송 | 직접 실행 | 직접 실행 |
| 클라이언트 | 아니요 | 버려짐 | 버려짐 | 직접 실행 |

여기에 `RplCondition` 평가가 더해지면, 표대로라면 실행되거나 전송될 호출도 버려질 수 있습니다.

표에서 두 가지를 기억해 두면 대부분의 실수를 피할 수 있습니다. 첫째, **소유자가 아닌 클라이언트가 보낸 `Server` RPC는 버려집니다.** 오류도 나지 않으니 "보냈는데 아무 일도 없는" 상황이 됩니다. 둘째, **서버에서 보낸 `Broadcast` RPC는 서버 자신에서는 실행되지 않습니다.**

### 브로드캐스트를 쓸 때 주의할 점

서버의 브로드캐스트는 클라이언트에서만 실행되므로, 리슨 서버의 호스트나 싱글플레이 플레이어에게도 같은 효과를 보이려면 서버에서 메서드를 직접 한 번 더 불러야 합니다. 공식 테스트 컴포넌트(`SCR_RplTestComponent`)가 정확히 이렇게 합니다.

```enforce
[RplRpc(RplChannel.Reliable, RplRcver.Server)]
protected void RpcAsk_PlaySiren()
{
	// 보안 검사가 필요하면 여기서 한다
	DoPlaySiren();				// 서버(리슨 서버 호스트 포함)에서 실행
	Rpc(RpcDo_PlaySiren);		// 클라이언트들에서 실행
}

[RplRpc(RplChannel.Reliable, RplRcver.Broadcast)]
protected void RpcDo_PlaySiren()
{
	DoPlaySiren();
}

protected void DoPlaySiren()
{
	// 소리나 이펙트 같은 프레젠테이션
}
```

또 하나, 브로드캐스트가 닿는 "관련 클라이언트"는 그 아이템이 **스트리밍되어 들어와 있는** 클라이언트뿐입니다. 멀리 있어서 아직 그 엔티티를 받지 않은 클라이언트나, 브로드캐스트 뒤에 접속한 클라이언트는 메시지를 받지 못합니다. 공식 주석도 브로드캐스트를 쓸 때는 "보낸 뒤에 아이템이 스트리밍되어 들어오면 어떻게 될지"를 늘 생각하라고 합니다. 그래서 다음처럼 나눠 쓰는 것이 원칙입니다.

- 계속 유지되는 **상태**(문이 열려 있다, 발전기가 켜져 있다)는 `[RplProp]`으로 복제합니다.
- 한 번 일어나고 끝나는 **사건**(사이렌이 울렸다, 폭발했다)은 브로드캐스트 RPC로 알립니다.

### 클라이언트의 요청을 서버로 보내기

월드에 놓인 발전기는 서버가 소유합니다. 그러니 클라이언트가 발전기 컴포넌트에서 `Server` RPC를 보내면 라우팅 표에 따라 버려집니다. 클라이언트가 자신이 소유한 무언가를 거쳐 요청해야 합니다.

공식 코드는 플레이어별 요청을 `PlayerController`에 붙인 컴포넌트로 처리합니다. 예를 들어 투표 기능의 `SCR_VoterComponent`는 `PlayerController`에 붙어 있고, 클라이언트에서 `Rpc(VoteServer, ...)`를 호출해 서버에 투표를 전달합니다. 서버 쪽 메서드는 요청한 플레이어를 클라이언트가 보낸 값이 아니라 `m_PlayerController.GetPlayerId()`로 확인합니다.

다음은 같은 방식으로 발전기를 켜고 끄는 요청 컴포넌트입니다. 대상은 `Replication.FindItemId()`로 얻은 `RplId`로 넘기고, 서버에서 `Replication.FindItem()`으로 되찾습니다.

```enforce title="Scripts/Game/TAG_GeneratorRequestComponent.c"
[ComponentEditorProps(category: "TAG/Tutorial", description: "발전기 조작 요청")]
class TAG_GeneratorRequestComponentClass : ScriptComponentClass
{
}

class TAG_GeneratorRequestComponent : ScriptComponent
{
	//! 이 PlayerController를 소유한 클라이언트에서 호출한다.
	void RequestSetRunning(notnull TAG_GeneratorComponent generator, bool running)
	{
		RplId generatorId = Replication.FindItemId(generator);
		if (!generatorId.IsValid())
			return;

		Rpc(RpcAsk_SetRunning, generatorId, running);
	}

	[RplRpc(RplChannel.Reliable, RplRcver.Server)]
	protected void RpcAsk_SetRunning(RplId generatorId, bool running)
	{
		// 서버에서 실행된다. 받은 값은 하나하나 검사한다.
		TAG_GeneratorComponent generator = TAG_GeneratorComponent.Cast(Replication.FindItem(generatorId));
		if (!generator)
			return;

		generator.SetRunning(running);
	}
}
```

`Replication.FindItemId()`는 내부에서 검색을 하므로 공식 주석은 빠른 반복문 안에서 쓰지 말라고 경고합니다. 요청할 때 한 번 부르는 정도는 문제없습니다.

이 컴포넌트를 쓰려면 게임 모드가 사용하는 `PlayerController` 프리팹에 붙여야 합니다. 기본 게임의 `{6E2BB64764E3BE9B}Prefabs/Characters/Core/DefaultPlayerController.et` 프리팹을 모드에 Override하고(**Override in** 메뉴) 이 컴포넌트를 추가하면 됩니다. 프리팹은 10장, 기존 게임 데이터를 모드에서 고치는 방법은 12장에서 다룹니다. 상호작용 메뉴로 동작하는 기능이라면 이런 요청 컴포넌트 없이도 서버에 동작을 전달할 수 있는 사용자 액션을 쓰는 편이 간단합니다. 16장에서 이 방법으로 프로젝트를 만듭니다.

<Tip title="서버에서 받은 요청은 검증합니다">

클라이언트는 조작될 수 있습니다. 서버 쪽 `RpcAsk_` 메서드에서는 대상이 실제로 있는지, 요청한 플레이어가 그 일을 할 수 있는 위치와 상태인지 확인한 뒤에 상태를 바꾸세요. 공식 `SCR_RplTestComponent`의 주석도 서버 RPC 안에서 보안 검사를 하라고 적고 있습니다.

</Tip>

### 스트리밍될 때 추가 데이터 보내기: RplSave와 RplLoad

`ScriptComponent`와 `GenericEntity`에는 `RplSave(ScriptBitWriter writer)`와 `RplLoad(ScriptBitReader reader)`라는 이벤트가 있습니다. `RplSave`는 아이템이 클라이언트로 스트리밍될 때 권한자에서 불리고, 거기서 쓴 데이터를 프록시의 `RplLoad`가 같은 순서로 읽습니다. 브로드캐스트 RPC로 상태를 알리는 컴포넌트가 중도 참가자에게 현재 상태를 전해 줄 때 쓰는 방법입니다(`SCR_ArsenalComponent` 참고).

```enforce
override bool RplSave(ScriptBitWriter writer)
{
	writer.WriteBool(m_bAlarmActive);
	writer.WriteInt(m_iAlarmLevel);
	return true;
}

override bool RplLoad(ScriptBitReader reader)
{
	bool active;
	int level;
	if (!reader.ReadBool(active) || !reader.ReadInt(level))
		return false;

	ApplyAlarm(active, level);	// 프레젠테이션 반영
	return true;
}
```

쓴 순서와 읽는 순서가 다르면 값이 뒤섞입니다. 또 위키는 `RplLoad`와 `[RplProp]` 값 갱신 사이의 순서가 보장되지 않는다고 경고합니다. `RplLoad` 안에서 다른 복제 속성의 값에 기대지 마세요. 대부분의 상태는 `[RplProp]`으로 충분하므로, 이 방법은 꼭 필요할 때만 씁니다.

## 엔티티 생성과 삭제, 계층 구조

### 생성은 서버에서

리플리케이션은 아이템이 언제 등록되는지에 따라 두 가지로 구분합니다(엔진 문서 Loadtime and Runtime).

- **로드타임(loadtime) 아이템**: 월드를 불러오는 동안 등록됩니다. 대개 월드에 미리 배치한 엔티티입니다. 서버와 클라이언트가 같은 월드 파일을 불러와 똑같이 만들어야 하며, 다르면 로그에 "inconsistent item table" 오류가 남고 클라이언트는 `JIP_ERROR`로 연결이 끊깁니다.
- **런타임(runtime) 아이템**: 게임이 진행되는 중에 서버에서 생성됩니다. 차량, 플레이어 캐릭터, 주울 수 있는 아이템이 전형적입니다. 반드시 프리팹으로 생성해야 하고, 서버에서만 등록할 수 있습니다. 클라이언트에는 필요할 때 프록시가 생깁니다.

클라이언트가 실행 중에 등록한 아이템은 **로컬(local) 아이템**이 되어 그 클라이언트에만 존재합니다. 엔진 문서에 따르면 Arma Reforger는 클라이언트에서 실수로 엔티티를 만드는 일을 막으려고 기본적으로 프리팹 생성을 서버에서만 허용합니다. 클라이언트 전용 엔티티가 꼭 필요하면 `GetGame().SpawnEntityPrefabLocal()`을 씁니다.

생성 코드 자체(`Resource.Load()`, `EntitySpawnParams`, `GetGame().SpawnEntityPrefab()`)는 10장에서 본 그대로이고, 권한자에서 실행하기만 하면 됩니다.

### 삭제

복제되는 엔티티는 권한자에서 `RplComponent.DeleteRplEntity(entity, false)`로 지웁니다. 공식 헬퍼 `SCR_EntityHelper.DeleteEntityAndChildren()`도 이 메서드를 감싼 것입니다. 공식 주석에 따르면 권한자가 호출하면 리플리케이션에서 제거한 뒤 엔티티를 실제로 지우고, 프록시가 호출하면 권한자가 지울 때까지 실제 삭제는 일어나지 않습니다. 두 번째 인수를 true로 주면 프록시 쪽 엔티티는 리플리케이션에서만 빠지고 지워지지 않습니다.

### 계층 구조와 RplComponent

엔진 문서(`RplDocs.c`)는 `RplComponent`가 노드를 만들 때 자식 엔티티까지 모을지를 이 컴포넌트의 "Recursive" 속성으로 정한다고 설명합니다(1.8.0.13 속성 목록에는 없는 이름입니다). 자식 엔티티에 따로 `RplComponent`가 있으면 그 자식은 별도 노드가 되어 부모 노드의 자식 노드로 연결됩니다. 엔진 문서와 `BaseRplComponent`의 주석에서 나온 규칙을 정리하면 다음과 같습니다.

- **노드의 아이템 목록은 등록 뒤에 바꿀 수 없습니다.** 실행 중에 다른 부모로 옮기거나 떼어 낼 엔티티는 자기 `RplComponent`를 가져야 합니다.
- `RplComponent`는 `EOnInit`에서 아이템을 모아 등록합니다. 공식 주석은 그 뒤에 생성한 것은 등록되지 않는다고 경고합니다.
- 프리팹의 **루트 엔티티에 `RplComponent`가 있어야** 합니다. 자식에만 있으면 실행 중 생성이나 중도 참가 때 노드를 프리팹과 연결하지 못합니다.
- 두 `RplComponent` 사이에 끼어 있는 중간 엔티티가 노드가 아니면, 중도 참가한 클라이언트에서 계층이 서버와 다르게 구성될 수 있습니다. 해결책은 중간 엔티티에도 `RplComponent`를 붙이거나 계층을 단순하게 바꾸는 것입니다.
- 초기화 중에 자식 엔티티를 생성할 때는 생성 과정에서 바로 부모에 붙입니다(`EntitySpawnParams.Parent`). 먼저 만들고 나중에 붙이면 부모와 따로 등록됩니다.

### 스트리밍과 중도 참가(JIP)

서버는 모든 엔티티를 모든 클라이언트에 보내지 않습니다. 리플리케이션 스케줄러가 클라이언트마다 각 노드 계층이 **관련(relevant)** 있는지 판단해, 필요한 것만 **스트리밍 인(streaming in)** 하고 필요 없어진 것은 **스트리밍 아웃(streaming out)** 합니다. 판단은 대부분 플레이어와의 거리에 기반하며, 노드 계층은 통째로 스트리밍됩니다.

런타임 아이템은 스트리밍 인 때 프록시가 생기고 스트리밍 아웃 때 사라집니다. 프록시가 있는 동안에만 상태를 받고 RPC를 주고받으므로, 클라이언트 코드는 "이 엔티티의 프록시가 내 기계에 없을 수도 있다"는 전제로 짭니다. 위키에 따르면 소유자의 기계에서는 소유권을 잃기 전까지 그 엔티티가 스트리밍 아웃되지 않습니다.

게임이 이미 진행 중일 때 접속하는 것을 <strong>중도 참가(Join In Progress, JIP)</strong>라고 합니다. 중도 참가자도 스트리밍으로 엔티티를 받으며, 이때 `[RplProp]` 값이 함께 전달되고 `onRplName` 콜백이 불립니다. 반면 접속하기 전에 보낸 브로드캐스트 RPC는 받지 못합니다. 앞에서 상태와 사건을 나눠 담으라고 한 이유가 여기에 있습니다.

## 흔한 실수

<Pitfall title="클라이언트에서 복제 속성을 바꾼다">

프록시에서 `[RplProp]` 변수를 바꿔도 다른 기계로 전달되지 않습니다. 그 클라이언트에서만 값이 달라졌다가, 권한자의 값이 바뀌어 다시 전달되면 덮어써집니다. 1.8.0.13에서 시험해 보면 권한자가 값을 바꾸지 않고 `Replication.BumpMe()`만 불렀을 때는 덮어써지지 않아, 클라이언트의 다른 값이 그대로 남았습니다. 상태 변경은 권한자에서만 하고, 클라이언트는 RPC로 요청합니다.

```enforce
void Toggle()
{
	m_bRunning = !m_bRunning;	// [!code --]
	Rpc(RpcAsk_Toggle);			// [!code ++]
}
```

`RpcAsk_Toggle`은 `RplRcver.Server` RPC이고, 그 안에서 값을 바꾼 뒤 `Replication.BumpMe()`를 부릅니다. 이 메서드를 가진 엔티티를 클라이언트가 소유하지 않았다면 앞 절처럼 소유한 객체를 거쳐 요청해야 합니다.

</Pitfall>

<Pitfall title="같은 효과가 두 번 실행된다">

리슨 서버의 호스트는 서버이면서 플레이어입니다. "로컬 효과를 바로 보여 주고(예측), 서버에도 요청하는" 코드를 쓰면 호스트에서 효과가 두 번 실행될 수 있습니다. 공식 `SCR_RplTestComponent`는 즉시 보여 주는 로컬 효과를 `IsOwnerProxy()`일 때만 실행하고, 서버가 다른 기계에 보내는 브로드캐스트에는 `RplCondition.NoOwner`를 붙여 소유자에게 다시 가지 않게 합니다.

</Pitfall>

## 정리

<Summary>

- 세션에는 서버가 하나뿐이고 클라이언트는 서버하고만 통신합니다. 서버가 시뮬레이션의 정답을 가지며, 싱글플레이는 접속을 받지 않는 리슨 서버와 같습니다.
- 복제 속성, RPC, 리플리케이션 콜백을 가진 엔티티·컴포넌트가 아이템이 되고, `RplComponent`가 이들을 노드로 묶어 등록합니다. 서버에서 만든 아이템만 공유됩니다.
- 아이템마다 권한자는 하나이고 나머지는 프록시입니다. 소유자는 서버로 RPC를 보낼 수 있는 단 하나의 클라이언트이며, 소유권은 권한과 별개입니다.
- 역할은 `RplComponent`의 `Role()`, `IsProxy()`, `IsOwner()` 등으로 확인하고, `Replication.IsServer()` 같은 환경 판단은 피합니다.
- 상태는 `[RplProp]` + `Replication.BumpMe()`로 복제합니다. `onRplName` 콜백은 프록시에서만 불리므로 권한자는 직접 호출합니다.
- RPC는 `[RplRpc(채널, 수신자)]`로 선언하고 `Rpc(메서드, 인수...)`로 호출합니다. 소유자가 아닌 클라이언트의 `Server` RPC는 버려지고, 서버의 `Broadcast`는 서버 자신에서 실행되지 않습니다.
- 유지되는 상태는 `[RplProp]`, 한 번 일어나는 사건은 브로드캐스트 RPC로 나눕니다. 브로드캐스트는 그 아이템을 스트리밍받은 클라이언트에만 닿습니다.
- 런타임 엔티티는 서버에서 프리팹으로 생성하고 `RplComponent.DeleteRplEntity()`로 지웁니다. 프리팹 루트에 `RplComponent`를 두고, 실행 중 계층을 바꿀 엔티티는 자기 `RplComponent`를 가져야 합니다.

</Summary>

<Exercise id="14-2" level="기초" title="복제되지 않는 점수">

다음 컴포넌트는 서버에서 `AddScore()`를 불러도 클라이언트의 점수 표시가 바뀌지 않습니다. 원인 두 가지를 찾아 고치세요. 엔티티에는 `RplComponent`가 있습니다.

```enforce
[ComponentEditorProps(category: "TAG/Tutorial", description: "점수판")]
class TAG_ScoreBoardComponentClass : ScriptComponentClass
{
}

class TAG_ScoreBoardComponent : ScriptComponent
{
	protected int m_iScore;

	void AddScore(int amount)
	{
		m_iScore += amount;
	}

	protected void OnScoreChanged()
	{
		PrintFormat("현재 점수: %1", m_iScore);
	}
}
```

</Exercise>

<Exercise id="14-3" level="응용" title="권한자에서도 같은 표시하기">

연습문제 14-2의 답에서 `OnScoreChanged()`는 프록시에서만 불립니다. 리슨 서버의 호스트와 싱글플레이에서도 점수가 출력되도록 고치고, `AddScore()`가 프록시에서 호출되면 아무 일도 하지 않게 만드세요. `AddScore()`에 0 이하의 값이 들어오면 무시합니다.

</Exercise>
