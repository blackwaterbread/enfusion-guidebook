표시 여부를 정하는 `CanBeShownScript()`를 고칩니다. 비어 있으면 false를 반환해 메뉴에서 빼면 됩니다.

```enforce
	override bool CanBeShownScript(IEntity user)
	{
		if (!m_Crate)
			return false;

		return m_Crate.GetRemaining() > 0;
	}
```

`CanBePerformedScript()`는 그대로 두어도 됩니다. 남은 수량은 복제된 값으로 계산하므로, 마지막 보급품을 누가 가져가면 모든 플레이어의 메뉴에서 항목이 사라집니다.

잃는 것은 **정보**입니다. 원래 설계에서는 빈 상자에 다가가도 "보급품 받기 (0/3)"이 보이고 "비어 있음"이라는 이유가 표시되므로, 플레이어는 "이 상자는 쓸 수 있는 상자인데 지금은 비었다"는 것을 압니다. 메뉴에서 빼면 상호작용할 수 없는 장식물과 구별되지 않습니다. 어느 쪽이 나은지는 게임 디자인의 문제입니다. 참고로 공식 샘플 모드의 `SCR_DrawerUserAction`과 `SCR_TrunkUserAction`은 `CanBeShownScript()`에서 `CanBePerformedScript()`의 결과를 그대로 돌려주므로, 실행할 수 없으면 숨기는 쪽을 택했습니다.

</Answer>

<Answer id="16-2">

보충 간격 어트리뷰트를 추가하고, 권한자에서만 콜 큐에 반복 호출을 등록합니다. `OnPostInit()`은 World Editor 편집 중에도 불리므로(10장) `GetGame().InPlayMode()`도 확인합니다. 바뀌는 부분만 보입니다.

```enforce
	[Attribute(defvalue: "60", desc: "하나를 다시 채우는 간격(초). 0이면 채우지 않음", params: "0 3600")]
	protected float m_fRefillInterval;

	override void OnPostInit(IEntity owner)
	{
		m_RplComponent = RplComponent.Cast(owner.FindComponent(RplComponent));
		if (!m_RplComponent)
		{
			Print("TAG_SupplyCrateComponent: 엔티티에 RplComponent가 없습니다.", LogLevel.ERROR);
			return;
		}

		// 보충은 게임 중에, 권한자에서만 돌린다
		if (GetGame().InPlayMode() && !m_RplComponent.IsProxy() && m_fRefillInterval > 0)
			GetGame().GetCallqueue().CallLater(Refill, m_fRefillInterval * 1000, true);
	}

	override void OnDelete(IEntity owner)
	{
		GetGame().GetCallqueue().Remove(Refill);
	}

	protected void Refill()
	{
		if (m_iTaken <= 0)
			return;	// 가득 차 있다

		m_iTaken--;
		Replication.BumpMe();
		OnTakenChanged();
	}
```

`Refill()`은 `TryTake()`와 똑같은 순서를 따릅니다. 복제 속성을 바꾸고, `Replication.BumpMe()`로 알리고, 권한자에서는 콜백을 직접 부릅니다. 타이머를 권한자에서만 등록했으므로 `Refill()` 안에서 역할을 다시 검사하지 않아도 됩니다. 클라이언트에서도 타이머가 돌면 각자 `m_iTaken`을 줄여 서버와 값이 어긋나게 됩니다(14장의 "클라이언트에서 복제 속성을 바꾼다").

`CallLater`의 지연 시간은 밀리초이므로 초 단위 어트리뷰트에 1000을 곱했습니다. 공식 `SCR_HintManagerComponent`도 `duration * 1000`처럼 같은 방식으로 넘깁니다.

</Answer>

<Answer id="16-3">

`ResourceName` 어트리뷰트에 프리팹을 고르게 하고, 서버에서만 실행되는 `TryTake()` 안에서 생성합니다.

```enforce
	[Attribute(defvalue: "", uiwidget: UIWidgets.ResourceNamePicker, desc: "지급할 프리팹", params: "et")]
	protected ResourceName m_sSupplyPrefab;

	//! 권한자에서만 부른다.
	protected void SpawnSupply()
	{
		if (m_sSupplyPrefab.IsEmpty())
			return;

		Resource resource = Resource.Load(m_sSupplyPrefab);
		if (!resource || !resource.IsValid())
			return;

		EntitySpawnParams params = new EntitySpawnParams();
		params.TransformMode = ETransformMode.WORLD;
		GetOwner().GetWorldTransform(params.Transform);
		params.Transform[3] = params.Transform[3] + "0 1 0";	// 상자 위치에서 위로 1미터

		GetGame().SpawnEntityPrefab(resource, GetOwner().GetWorld(), params);
	}
```

`TryTake()`에서는 `OnTakenChanged();` 다음 줄에 `SpawnSupply();`를 넣습니다. `TryTake()`는 프록시에서 바로 반환하므로 생성은 서버에서만 일어납니다. 변환 행렬의 네 번째 행 `Transform[3]`이 위치이고, `vector`에 `"0 1 0"` 같은 문자열 리터럴을 더하는 것은 공식 코드에도 있는 관용구입니다.

생성할 프리팹의 루트에 `RplComponent`가 있어야 클라이언트에도 보입니다(14장). 엔진 문서에 따르면 Arma Reforger는 기본적으로 프리팹 생성을 서버에서만 허용하므로, 서버에서 만드는 이 설계가 엔진의 규칙과도 맞습니다.

</Answer>

<Answer id="16-4">

받은 플레이어 목록은 서버만 알면 되므로 `[RplProp]` 없이 평범한 멤버 변수 `set<int>`로 둡니다. 거절 이유도 알려 줘야 하므로, 본문의 힌트 RPC를 문자열을 받는 범용 RPC로 바꿉니다. 바뀌는 부분만 보입니다.

```enforce
	//! 이미 받은 플레이어 ID. 서버에서만 쓰고 복제하지 않는다.
	protected ref set<int> m_TakenPlayerIds = new set<int>();

	bool TryTake(IEntity user)
	{
		if (!user || !m_RplComponent || m_RplComponent.IsProxy())
			return false;

		int playerId = GetGame().GetPlayerManager().GetPlayerIdFromControlledEntity(user);
		if (GetRemaining() <= 0)
		{
			NotifyPlayer(playerId, "비어 있습니다.");
			return false;
		}

		if (playerId > 0 && m_TakenPlayerIds.Contains(playerId))
		{
			NotifyPlayer(playerId, "이미 받았습니다.");
			return false;
		}

		m_iTaken++;
		Replication.BumpMe();
		OnTakenChanged();

		if (playerId > 0)
			m_TakenPlayerIds.Insert(playerId);

		NotifyPlayer(playerId, string.Format(m_sHintText, GetRemaining()));
		return true;
	}
```

알림 부분은 다음과 같습니다. 본문의 `RpcDo_NotifyTaken()`과 `ShowTakenHint()`를 대신합니다.

```enforce
	//! 권한자에서 부른다. 해당 플레이어의 기계에서만 힌트가 뜬다.
	protected void NotifyPlayer(int playerId, string text)
	{
		if (playerId <= 0)
			return;

		ShowHintFor(playerId, text);			// 리슨 서버 호스트, 싱글플레이
		Rpc(RpcDo_ShowHint, playerId, text);	// 원격 클라이언트
	}

	[RplRpc(RplChannel.Reliable, RplRcver.Broadcast)]
	protected void RpcDo_ShowHint(int playerId, string text)
	{
		ShowHintFor(playerId, text);
	}

	protected void ShowHintFor(int playerId, string text)
	{
		if (playerId != SCR_PlayerController.GetLocalPlayerId())
			return;

		SCR_HintManagerComponent.ShowCustomHint(text, m_sHintTitle, 5);
	}
```

설계에서 짚을 점은 세 가지입니다.

- **검사는 서버에서**: 클라이언트는 누가 받았는지 모르므로 `CanBePerformedScript()`는 여전히 실행 가능으로 판단합니다. 플레이어가 상호작용하면 서버가 거절하고 이유를 알려 줍니다. 클라이언트에 목록을 복제해 메뉴에서 미리 막을 수도 있지만, 그만큼 네트워크로 보낼 데이터가 늘어납니다.
- **거절도 피드백**: 본문 설계의 한계였던 "먼저 가져간 사람이 있어 거절된 경우"도 이제 "비어 있습니다" 힌트로 알 수 있습니다.
- **RPC 인수에 문자열**: 공식 코드에도 `RpcDo_SetFactionTasksEnabled(string factionKey, ...)`처럼 문자열 인수를 받는 RPC가 있습니다. 다만 문구를 바꿀 때마다 서버를 고쳐야 하므로, 실제 모드라면 거절 이유를 정수 코드로 보내고 문구는 클라이언트 쪽 어트리뷰트에서 고르는 편이 낫습니다.

</Answer>

<Answer id="16-5">

`SCR_HintUIInfo`를 어트리뷰트로 받고, 설명에 들어 있는 `%1`을 남은 수량으로 채워 보여 줍니다. `SetDescription()`은 설명을 덮어쓰므로, 처음 설정된 설명(서식 문자열)은 `OnPostInit()`에서 따로 저장해 둡니다. 바뀌는 부분만 보입니다.

```enforce
	[Attribute(desc: "보급품을 받았을 때 보일 힌트. 설명의 %1은 남은 수량")]
	protected ref SCR_HintUIInfo m_TakenHint;

	protected string m_sHintTemplate;	// 처음 설정된 설명

	override void OnPostInit(IEntity owner)
	{
		m_RplComponent = RplComponent.Cast(owner.FindComponent(RplComponent));
		if (!m_RplComponent)
			Print("TAG_SupplyCrateComponent: 엔티티에 RplComponent가 없습니다.", LogLevel.ERROR);

		if (m_TakenHint)
			m_sHintTemplate = m_TakenHint.GetUnformattedDescription();
	}

	protected void ShowTakenHint(int playerId, int remaining)
	{
		if (playerId != SCR_PlayerController.GetLocalPlayerId())
			return;

		if (!m_TakenHint)
			return;	// Workbench에서 힌트를 설정하지 않았다

		m_TakenHint.SetDescription(string.Format(m_sHintTemplate, remaining));
		SCR_HintManagerComponent.ShowHint(m_TakenHint, false, true);
	}
```

본문의 `m_sHintTitle`, `m_sHintText` 어트리뷰트는 이제 필요 없으니 지웁니다. 제목, 지속 시간, 우선순위 같은 나머지 설정은 Workbench에서 `m_TakenHint`의 속성으로 정합니다(Hint Usage 문서, 13장).

`ShowHint(info, isSilent, ignoreShown)`의 세 번째 인수를 true로 준 이유는, 힌트에 종류(Type)가 지정되어 있으면 정해진 횟수 이상 보이지 않기 때문입니다(`SCR_HintManagerComponent.WasShown()`). 보급품을 받을 때마다 보여야 하는 힌트이므로 이 검사를 건너뜁니다. `SetDescription()`의 공식 주석은 이미 표시 중인 힌트를 바꿨다면 `SCR_HintManagerComponent.Refresh()`를 부르라고 안내하는데, 여기서는 바꾼 뒤 곧바로 `ShowHint()`로 다시 띄우므로 따로 부르지 않아도 됩니다. 1.8.0.13에서 시험해 보면 힌트가 떠 있는 동안 같은 상자를 다시 쓸 때는 같은 `m_TakenHint`를 다시 띄우게 되어, 두 번째 힌트는 무음으로 처리되었고(로그의 `silent=1`), 새 수량이 담긴 설명으로 다시 표시 이벤트가 나갔습니다. 공식 코드가 표시 중인 같은 힌트를 다시 띄우면 항상 소리를 끄기 때문입니다(`isSilent |= m_bIsShown && info == m_LatestHint`).

본문 방식에서도 제목과 문구는 어트리뷰트였지만, 지속 시간(5초)은 코드에 적혀 있었습니다. 이 방식에서는 지속 시간까지 포함한 힌트 설정이 모두 Workbench의 `m_TakenHint` 한곳에 모입니다.

</Answer>
