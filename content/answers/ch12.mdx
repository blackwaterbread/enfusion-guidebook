<Answer id="12-1">

고칠 곳은 다음과 같습니다.

- 열거형: 태그가 없고, `E` 접두사가 없고, 이름이 복수형이며, 값이 소문자입니다. → `ABC_EFireMode`, `SINGLE`, `BURST`
- 클래스: 태그가 없고 이름이 복수형입니다. → `ABC_WeaponHelper` (파일 이름도 `ABC_WeaponHelper.c`)
- 상수: 대문자와 밑줄로 씁니다. → `MAX_AMMO`
- 멤버 변수: `m_`과 타입 접두사가 필요합니다. → `m_iAmmo`, `m_bLoaded`
- 메서드는 PascalCase, 매개변수는 camelCase입니다. → `Reload(int amount)`
- 중괄호는 새 줄에 둡니다(Allman 스타일).

```enforce
enum ABC_EFireMode
{
	SINGLE,
	BURST
}

class ABC_WeaponHelper
{
	protected int m_iAmmo;
	protected bool m_bLoaded;

	static const int MAX_AMMO = 30;

	void Reload(int amount)
	{
	}
}
```

Conventions 문서의 선언 순서에 맞춰 상수는 멤버 변수 뒤로 옮겼습니다. 상수에는 `m_`이나 `s_`를 붙이지 않습니다.

</Answer>

<Answer id="12-2">

원래 동작(구독자에게 알리고 통계 API에 전달하는 일)은 `super`로 그대로 실행하고, 그 뒤에 로그를 남깁니다. 시그니처는 원본과 똑같이 맞춥니다.

```enforce title="Scripts/Game/Modded/TAG_BaseScoringSystemComponent.c"
modded class SCR_BaseScoringSystemComponent
{
	override protected void OnPlayerScoreChanged(int playerId, SCR_ScoreInfo scoreInfo)
	{
		super.OnPlayerScoreChanged(playerId, scoreInfo);

		if (scoreInfo)
			PrintFormat("[TAG] 플레이어 %1의 처치 수: %2", playerId, scoreInfo.m_iKills);
	}
}
```

- 파일은 원본(`Scripts/Game/GameMode/Scoring/SCR_BaseScoringSystemComponent.c`)과 다른 경로에, 태그를 붙인 이름으로 두었습니다. 같은 경로·이름이면 원본 파일이 통째로 대체됩니다.
- 공식 주석에 따르면 이 메서드는 점수가 바뀔 때 모든 기계에서 불리므로, 로그도 서버와 각 클라이언트에 모두 남습니다.
- `super`를 먼저 부르면 원래 동작이 끝난 뒤에 로그가 남습니다. 원래 동작보다 먼저 무언가를 해야 한다면 `super` 앞에 둡니다.

</Answer>

<Answer id="12-3">

모드 B가 모드 A에 의존하므로 적용 순서는 원본 → 모드 A → 모드 B입니다. 실제로 만들어지는 것은 모드 B의 버전이고, 각 `super`는 바로 앞 단계를 부릅니다.

```text
A: 삐걱 소리
원본: 문이 열린다
B: 문 열림 기록
```

모드 B의 `super.Open()`이 모드 A의 `Open()`을 부르고, 모드 A는 자기 출력 뒤에 `super.Open()`으로 원본을 부릅니다. 원본이 끝나면 다시 모드 B로 돌아와 마지막 줄을 출력합니다.

모드 B의 `super.Open()`을 `vanilla.Open()`으로 바꾸면 모드 A를 건너뛰고 원본을 바로 부릅니다.

```text
원본: 문이 열린다
B: 문 열림 기록
```

모드 A의 삐걱 소리가 사라졌습니다. `vanilla`는 다른 모드의 수정을 무시하므로, 모드끼리 함께 쓰일 것을 생각하면 `super`가 기본이고 `vanilla`는 원본 동작만 꼭 필요할 때 씁니다. 두 모드 사이에 의존 관계가 없었다면 A와 B 가운데 어느 쪽이 나중에 적용될지 보장되지 않으므로 첫 번째 출력의 순서도 장담할 수 없습니다.

</Answer>

보상 항목과 최상위 설정 클래스를 만들고, 컴포넌트는 설정 파일을 `ResourceName` 어트리뷰트로 받아 `SCR_ConfigHelperT`로 불러옵니다.

```enforce title="Scripts/Game/TAG_RewardTableConfig.c"
[BaseContainerProps(), BaseContainerCustomTitleField("m_sName")]
class TAG_RewardEntry
{
	[Attribute(desc: "보상 이름")]
	string m_sName;

	[Attribute(defvalue: "1", desc: "필요한 처치 수", params: "1 1000")]
	int m_iRequiredKills;

	[Attribute("", UIWidgets.ResourceNamePicker, desc: "지급할 프리팹", params: "et")]
	ResourceName m_sPrefab;
}

[BaseContainerProps(configRoot: true)]
class TAG_RewardTableConfig
{
	[Attribute("", UIWidgets.Object, desc: "보상 목록")]
	ref array<ref TAG_RewardEntry> m_aRewards;
}
```

```enforce title="Scripts/Game/TAG_RewardComponent.c"
[ComponentEditorProps(category: "TAG/Tutorial", description: "처치 수에 맞는 보상을 찾습니다")]
class TAG_RewardComponentClass : ScriptComponentClass
{
}

class TAG_RewardComponent : ScriptComponent
{
	[Attribute("", UIWidgets.ResourceNamePicker, desc: "보상 표",
		params: "conf class=TAG_RewardTableConfig")]
	protected ResourceName m_sRewardTable;

	protected ref TAG_RewardTableConfig m_RewardTable;

	override void OnPostInit(IEntity owner)
	{
		m_RewardTable = SCR_ConfigHelperT<TAG_RewardTableConfig>.GetConfigObject(m_sRewardTable);
	}

	TAG_RewardEntry FindReward(int kills)
	{
		if (!m_RewardTable || !m_RewardTable.m_aRewards)
			return null;

		TAG_RewardEntry best;
		foreach (TAG_RewardEntry entry : m_RewardTable.m_aRewards)
		{
			if (!entry || entry.m_iRequiredKills > kills)
				continue;

			if (!best || entry.m_iRequiredKills > best.m_iRequiredKills)
				best = entry;
		}

		return best;
	}
}
```

- 불러온 설정 객체는 `ref` 멤버가 들고 있어야 사라지지 않습니다. 반대로 `FindReward()`가 돌려주는 항목은 그 객체 안에 있으므로 약한 참조로 돌려줘도 됩니다.
- 설정 파일에 배열을 하나도 채우지 않으면 `m_aRewards`가 null일 수 있어 함께 검사했습니다.
- 설정 파일은 Resource Browser의 **Create** 버튼에서 **Config file**을 고르고 `TAG_RewardTableConfig` 클래스를 선택해 만듭니다.

</Answer>

<Answer id="12-5">

쓰는 쪽은 `StartArray`에 항목 수를 미리 넘기고, 플레이어마다 `StartObject`와 `EndObject` 사이에 값을 씁니다. 읽는 쪽은 같은 이름으로 `StartArray`를 불러 항목 수를 받은 뒤 같은 구조를 따라 읽습니다.

```enforce
class TAG_SessionJson
{
	static string Save(notnull map<string, int> kills)
	{
		JsonSaveContext context = new JsonSaveContext();
		int count = kills.Count();
		context.StartArray("players", count);	// 개수는 미리 알려 준다
		foreach (string playerName, int playerKills : kills)
		{
			context.StartObject();
			context.WriteValue("name", playerName);
			context.WriteValue("kills", playerKills);
			context.EndObject();
		}
		context.EndArray();

		return context.SaveToString();
	}

	// Load()는 아래에 이어진다
}
```

```enforce
static bool Load(string json, notnull map<string, int> outKills)
{
	JsonLoadContext context = new JsonLoadContext();
	if (!context.LoadFromString(json))
		return false;

	int count;
	if (!context.StartArray("players", count))	// 읽을 때는 개수를 받는다
		return false;

	for (int i = 0; i < count; i++)
	{
		string playerName;
		int playerKills;
		if (!context.StartObject())
			return false;

		if (!context.ReadValue("name", playerName) || !context.ReadValue("kills", playerKills))
			return false;

		context.EndObject();
		outKills.Set(playerName, playerKills);
	}

	return context.EndArray();
}
```

- `StartArray(string name, out int count)`의 `count`는 쓸 때는 미리 알려 주는 개수이고, 읽을 때는 배열에 든 항목 수를 받아 오는 값입니다.
- 결과 맵은 `notnull` 매개변수로 받아 채웠습니다. 호출하는 쪽이 맵을 만들어 넘기므로 맵의 수명을 호출하는 쪽이 관리합니다.
- 각 단계의 반환값을 확인해, JSON이 기대한 구조가 아니면 `false`를 돌려줍니다.

</Answer>
