```enforce title="Scripts/Game/TAG_Grader.c"
class TAG_Grader
{
	//------------------------------------------------------------------------------------------------
	static string GetGrade(int score)
	{
		// 처리할 수 없는 값은 첫머리에서 걸러 냅니다.
		if (score < 0 || score > 100)
			return "invalid";

		if (score >= 90)
			return "A";

		if (score >= 75)
			return "B";

		if (score >= 50)
			return "C";

		return "F";
	}

	//------------------------------------------------------------------------------------------------
	static void Test()
	{
		Print("95 -> " + GetGrade(95));
		Print("75 -> " + GetGrade(75));
		Print("49 -> " + GetGrade(49));
		Print("120 -> " + GetGrade(120));
	}
}
```

`TAG_Grader.Test();`의 실행 결과는 다음과 같습니다.

```text
95 -> A
75 -> B
49 -> F
120 -> invalid
```

- 각 조건에서 바로 `return`하므로 `else if`를 쓰지 않아도 위에서부터 차례로 검사됩니다. `if`/`else if`/`else`로 써도 결과는 같습니다.
- `Test()`의 75처럼 경계값을 넣어 시험해 보면 `>`와 `>=`를 헷갈린 실수를 잡을 수 있습니다.
- 메서드가 모든 경로에서 값을 돌려주도록 마지막 줄에 `return "F";`를 두었습니다.

```enforce title="Scripts/Game/TAG_Commands.c"
class TAG_Commands
{
	//------------------------------------------------------------------------------------------------
	static void Execute(string command)
	{
		switch (command)
		{
			case "heal":
			case "medic":
				Print("Healing");
				break;

			case "reload":
				Print("Reloading");
				break;

			case "retreat":
			case "fallback":
				Print("Falling back");
				break;

			default:
				Print("Unknown: " + command);
				break;
		}
	}
}
```

- 코드 없는 `case` 라벨을 겹쳐 별칭이 같은 코드를 쓰게 했습니다.
- 각 `case`를 `break`로 끝냈습니다. 첫 번째 `case`에서 빠뜨리면 컴파일 오류가 나고, 다른 `case`에서 빠뜨리면 다음 `case`의 출력까지 이어집니다(본문의 fall-through 설명 참고).
- 문자열 비교는 대소문자를 구분하므로 `"Heal"`은 `default`로 갑니다. 대소문자를 무시하려면 `switch` 앞에서 소문자로 바꿉니다. `string`의 `ToLower()`는 원본 문자열을 직접 바꾸고 길이를 돌려주므로, 복사본을 만든 뒤 부릅니다(9장).

```enforce title="Scripts/Game/TAG_HitAnalyzer.c"
class TAG_HitAnalyzer
{
	//------------------------------------------------------------------------------------------------
	static void Run()
	{
		array<int> hits = { 12, -3, 40, 0, 25, -1, 60 };

		int sum;
		int positiveCount;
		foreach (int hit : hits)
		{
			if (hit <= 0)
				continue;           // 0 이하는 건너뜀

			sum += hit;
			positiveCount++;
		}

		int firstBigIndex = -1;
		foreach (int index, int hit : hits)
		{
			if (hit >= 50)
			{
				firstBigIndex = index;
				break;              // 처음 찾은 곳에서 멈춤
			}
		}

		PrintFormat("sum %1, count %2, first >= 50 at %3", sum, positiveCount, firstBigIndex);
	}
}
```

실행 결과는 다음과 같습니다.

```text
sum 137, count 4, first >= 50 at 6
```

- 합은 12, 40, 25, 60을 더한 137이고, 양수는 네 개입니다.
- `sum`과 `positiveCount`는 선언만 했지만 `int`의 기본값 0에서 시작합니다.
- 50 이상인 첫 값 60은 인덱스 6에 있습니다. 찾은 뒤에는 더 볼 필요가 없으므로 `break`로 반복을 끝냅니다. 못 찾았을 때를 위해 `firstBigIndex`를 -1로 시작했습니다.

</Answer>

```enforce title="Scripts/Game/TAG_AmmoReport.c"
class TAG_AmmoReport
{
	//------------------------------------------------------------------------------------------------
	static void Report(map<string, int> ammo)
	{
		if (!ammo || ammo.IsEmpty())
		{
			Print("none");
			return;
		}

		int total;
		string bestWeapon;
		int bestRounds = int.MIN;
		foreach (string weapon, int rounds : ammo)
		{
			total += rounds;

			// 탄약 수가 같으면 이름이 사전순으로 앞선 무기를 고릅니다.
			if (rounds > bestRounds || (rounds == bestRounds && weapon.Compare(bestWeapon) < 0))
			{
				bestRounds = rounds;
				bestWeapon = weapon;
			}
		}

		Print("total " + total);
		Print("most ammo: " + bestWeapon + " (" + bestRounds + ")");
	}

	//------------------------------------------------------------------------------------------------
	static void Test()
	{
		map<string, int> ammo = new map<string, int>();
		ammo.Insert("rifle", 120);
		ammo.Insert("pistol", 45);
		ammo.Insert("launcher", 2);
		Report(ammo);
	}
}
```

`TAG_AmmoReport.Test();`의 실행 결과는 다음과 같습니다.

```text
total 167
most ammo: rifle (120)
```

- `null`과 빈 맵을 첫머리에서 함께 걸러 냅니다. 맵도 객체이므로 `if (ammo)`는 `null`인지만 봅니다.
- 최댓값의 시작값으로 `int.MIN`을 썼습니다. 공식 코드도 최댓값을 찾을 때 `int maxSize = int.MIN;`처럼 시작합니다.
- 합계는 순서와 상관없이 같습니다. 하지만 탄약 수가 같은 무기가 둘 이상이면, `rounds > bestRounds`만으로는 먼저 순회한 무기가 뽑히고 맵의 순회 순서는 보장되지 않으므로 결과가 바뀔 수 있습니다. 그래서 `string.Compare`로 이름을 비교해 항상 같은 무기를 고르게 했습니다. `a.Compare(b)`는 `a`가 사전 순으로 `b`보다 앞서면 0보다 작은 값을 돌려줍니다.

```enforce title="Scripts/Game/TAG_RetryDemo.c"
class TAG_RetryDemo
{
	//------------------------------------------------------------------------------------------------
	static void Run()
	{
		int maxTries = 50;
		int tries;
		int value;
		bool success;

		while (true)                          // 조건이 참이므로 본문이 적어도 한 번 실행됨
		{
			value = Math.RandomIntInclusive(1, 100);
			tries++;

			if (value >= 95)
			{
				success = true;
				break;
			}

			if (tries >= maxTries)            // 안전장치
				break;
		}

		if (success)
			PrintFormat("Success: %1 after %2 tries", value, tries);
		else
			PrintFormat("Gave up after %1 tries", tries);
	}
}
```

- `while (true)`로 시작해 본문 끝에서 조건을 검사하면 `do-while`과 같은 흐름이 됩니다.
- 시도 횟수를 세고 50번이 되면 `break`합니다. 성공했는지는 `success`로 구별합니다.
- `Math.RandomIntInclusive(1, 100)`은 1과 100을 모두 포함한 범위에서 뽑습니다. 끝을 포함하지 않는 `Math.RandomInt(min, max)`와 헷갈리지 않도록 주의합니다.

최대 시도 횟수가 없으면, 확률이 낮은 일이 오래 일어나지 않을 때 반복이 길어집니다. 더 위험한 것은 조건에 실수가 있는 경우입니다. 예를 들어 `value >= 101`처럼 절대 참이 될 수 없는 조건을 쓰면 반복이 끝나지 않습니다. 스크립트는 협력형으로 실행되어 이 반복문이 다른 코드에 차례를 넘기지 않으므로 게임이 멈추고, 프리즈 감지 시간(기본 300초)이 지나면 게임은 강제로 크래시합니다.

</Answer>
